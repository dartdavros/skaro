## Цели и границы

1. Разрешать межзадачные блокеры без переноса сообщений владельцем между чатами.
2. Сохранять параллелизм и выполнять одно согласованное действие над общим ресурсом.
3. Сократить лишние подтверждения, повторные подготовки окружений и C4-ревью.
4. Ограничить расход диска, RAM и квоты; освобождать ресурсы по проверяемым правилам.
5. Сохранять работу и решения при перезапуске, сбое модели и смене исполнителя.

План не меняет код, права, данные проектов или настройки установленного Skaro
самим фактом принятия. Он не создаёт задачи приложения, не разрешает релиз
и не включает автоматический запуск всего backlog.

Контракты разделены: [архиагент](archiagent.md),
[ресурсы](project-resources.md), [C4](c4-workflow.md).
Подробные шаги, результаты и критерии каждого этапа находятся в планах
[координации](archiagent-coordination-plan.md),
[ресурсов](archiagent-resource-plan.md), [C4](archiagent-c4-plan.md).
Эти документы составляют один план; идентификаторы этапов ниже устойчивы.

## Общие подготовительные условия

- Зафиксировать исходную ревизию, состав существующих незакоммиченных правок
  cleanup и их отдельные результаты проверки; не перезаписывать чужую работу.
- Для каждого этапа определить изменяемые сервисы, владельца состояния,
  версии схем и обратную совместимость. Переиспользовать текущие исполнители
  задач, интеграции, журнал команд, вопросы, Git и environment services.
- До записи из двух чатов определить сериализацию общего ресурса и проверку
  актуальности решения; параллельное чтение не требует глобальной блокировки.
- Новые структуры событий и запросов не содержат credentials или полного
  вывода команд по умолчанию; подробности доступны по защищённым ссылкам/ID.
- Численные пределы ресурсов, интервалы ожидания и политика хранения фиксируются
  при RC-2 по измерениям и возможностям платформы. Неизвестный размер не равен нулю.
- Восстановление неоднозначной внешней операции начинается со сверки состояния,
  а не с повторного применения. Отсутствие идемпотентности сервиса явно учитывается.

## UI-решения до зависимого кода

AC-4 согласован и реализован в [UI baseline](ui-baseline.md). Макет C4-3
[утверждён владельцем](archiagent-c4-3-design-proposal.md); реализация сохраняет текущие компоненты:

- окно решения текущего проекта: открытие, ожидание, ошибка, отложенное решение,
  несколько запросов, переход проекта и возврат после перезапуска;
- размещение и объяснение трёх режимов прав без расширения прежних разрешений;
- представление сохраняемых важных событий в существующей фоновой модалке;
- место, точный текст и состояния действия полного аудита в разделе C4.

Окно и закреплённая карточка показывают одну сущность решения. Закрытие окна
не скрывает ожидающее действие из открытой ленты и не отвечает на него.
Без согласованной компоновки зависимые UI-правки остаются за design gate;
это не мешает независимой работе над контроллером и ресурсами.

## AG-1. Совместная приёмка и включение

Результат: пользователь ведёт проект через архиагента, блокеры проходят полный
цикл, новая политика C4 и ресурсы работают совместно, существующая работа сохранена.

Работы:

1. Проверить совместимость схем и миграций трёх направлений; определить единый
   барьер включения нового владельца операций и исключить двойное исполнение.
2. Выполнить сценарии таблицы ниже на штатном Cat-pilot с реальными сервисами.
   История Stolovka служит обоснованием требований, не новым проверочным проектом.
3. Сравнить измерения до/после на сопоставимых сценариях; объяснить отклонения.
4. Проверить отключение новых запусков и безопасное завершение/удержание уже
   начатых операций. Откат схем не должен терять новые решения или историю;
   при несовместимости старый путь блокируется, а не читает их неверно.
5. Обновить статус в общем плане и профильных контрактах по фактическим
   свидетельствам. Согласовать release-процедуру отдельно, если нужен выпуск.

| Сценарий | Критерий приёмки |
| --- | --- |
| Общая причина блокирует две задачи | Одна операция устранения; максимум один необходимый вопрос; обе разрешённые задачи продолжаются после проверки эффекта |
| Чат устраняет проблему задачи | Контекст и результат доходят без копирования текста и ручной команды «продолжи»; остановленная владельцем задача не запускается |
| Зависимость изменилась во время ожидания | Перед продолжением проверены новые входы; незакоммиченная работа сохранена; проверки относятся к точной версии |
| Проверка требует локальной выкладки до Git-приёмки | Разрешённая версия проверяется в зарегистрированном постоянном контуре без преждевременного слияния или подмены приёмки |
| Исчерпана квота общей модели | Видно ожидание квоты; нет цикла model retries; ненужные ресурсы освобождены; housekeeping работает без LLM |
| Несколько проектов конкурируют за ресурсы | Общий бюджет соблюдён; ожидающая работа не создаёт лишние тяжёлые копии; очередь не допускает бесконечного голодания |
| Ответ через окно, чат и повтор после сбоя | Применён один эффект; устаревший fingerprint не даёт выполнить изменённую операцию |
| Изменение принято, обычная реализация завершена | Техническая актуализация C4 не требует отдельного действия владельца; evidence и публикация проверены |
| Обнаружено новое существенное решение | Одно согласование связанных артефактов; ждёт только зависимая работа; отказ не применяется и не предлагается повторно без основания |
| Задача завершена, основной контур нужен другим | Одноразовые ресурсы освобождены; основной контур, данные и активные потребители сохранены |
| Docker недоступен или ресурс не опознан | Безопасное ожидание очистки с видимой причиной; отсутствие данных не трактуется как разрешение удаления |
| Перезапуск во время миграции/операции | Нет двух координаторов-писателей, потерянных вопросов, повторных внешних эффектов или исчезнувших результатов |

- [x] Ни одна подтверждённая операция не выполнена повторно; неопределённые

- [x] Обычный технический блокер снимается без передачи сообщений между чатами;

- [x] Измерены освобождение ресурсов и сохранность данных, а не только вызовы cleanup.
- [x] Проверены фактический UI, восстановление и длительная история; нет

## Измерения результата

До внедрения фиксируется база по выбранным сценариям; после — те же показатели:

| Показатель | Что считать успешным результатом |
| --- | --- |
| Участие владельца | Ноль ручных передач между чатами для разрешённого технического исправления; одно решение на один существенный связанный выбор |
| Разрешение блокера | От обнаружения до проверенного снятия, отдельно ожидание человека/квоты и работа системы |
| Расход модели | Вызовы/токены координатора и исполнителей отдельно; housekeeping не вызывает модель; нет холостых циклов |
| Подготовка окружения | Ожидание слота, build/setup/readiness отдельно; повторное использование измерено по совместимому fingerprint |
| Ресурсы | Пиковые RAM/диск, свободный резерв, число окружений, фактически освобождённые байты и причины удержания |
| C4 | Число ручных подтверждений технической актуализации равно нулю; повторное ревью объясняется изменением затронутых входов |
| Надёжность | Ноль потерянных решений, двойных эффектов и удалений постоянных/неизвестных ресурсов в проверенных сценариях |

Не обещать фиксированное ускорение или объём освобождения без измерений.
Остановка контейнеров и возврат места файловой системе хоста учитываются
раздельно; освобождение внутри Docker не выдаётся за уменьшение его диска на Windows.

## Проверки и правила выполнения плана

- Для текущей документационной работы сборка и runtime-тесты не запускаются.
- При будущих изменениях кода: сборка и только тесты изменённого поведения
  и непосредственно затронутых сценариев. Полный прогон — перед релизом
  либо по прямому указанию владельца.
- Новые тесты покрывают значимые инварианты, конфликты и восстановление;
  тесты ради количества и дублирование реализации не нужны.
- Mock API, fake backend, временные серверы, fixtures и seed не разрешаются
  этим планом. При недоступности штатного контура фиксируется blocker.
- Живые agent/browser/MCP/workflow проверки — только зарегистрированный Cat-pilot
  по [границам запуска](builtin-agent-project-scope.md). Chatballs исключён
  также из восстановления, индексации и cleanup проверочного запуска.
- Для UI обязательна browser-проверка настоящего приложения и сверка с baseline,
  включая pending-состояния, навигацию, перезапуск и пагинацию истории.
- Новые/изменённые компоненты соблюдают SRP и разделение ответственности:
  около 180 строк для компонента, около 300 для файла; рост требует декомпозиции.
- Свидетельство приёмки содержит ревизию, платформу/адаптер, реальный сценарий,
  команды/результаты, снимки UI при необходимости и непроверенные ограничения.
  Описание целевого поведения и историческая проверка не закрывают новый этап.
