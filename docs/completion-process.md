# Завершение задач, этапов и релизов

По поручению владельца от 31.10.2026 запуск задачи означает выполнение до
проверенной сдачи результата. Завершение отдельного хода модели не переводит
незавершённую задачу в ожидание пустого ответа: Skaro продолжает её через общую
очередь. Конкретные вопросы и архитектурные пакеты сохраняют свои решения;
после ответа работа продолжается. Невыполненные критерии агент доделывает,
а не предлагает автоматически принять как выполненные. Автовливание использует
существующую настройку и проверки; это правило не обход приёмки или слияния.

Намерение выполнения, явная остановка и доказанный внешний блокер сохраняются
за запуском. После перезапуска возобновляется только неостановленная задача
без открытого решения или блокера. Повтор терминального события не создаёт
второе продолжение. Два повторных завершения без изменения кода, приёмки,
архитектуры или подготовки окружения прекращают автоповторы с явной ошибкой,
чтобы не расходовать лимит бесконечно. Служебные команды продолжения остаются
доказательством доставки, но не показываются как сообщения владельца.

Решение владельца от 06.10.2026 заменяет D-38: этап не создаёт задачу с
идентификатором Mxx, сессию агента или отдельный чат. Архивные логи таких сессий
сохраняются на диске. План остаётся группировкой реальных задач.

## Слияние по одной задаче (D-45, 12.10.2026)

Решение владельца от 12.10.2026 заменяет слияние этапов и интеграцию публикации.
Разделы ниже действуют в части хранения результатов, восстановления, CI и
сохранности данных; всё, что в них сказано о слиянии этапа целиком, частичном
слиянии и кандидате публикации, больше не действует.

- **Единица слияния — задача.** Завершённая задача вливается сразу: при включённом
  «Вливать автоматически» — без участия владельца, при выключенном — карточкой в
  чате этой задачи. Этап остаётся группой плана; пункта «Влить готовое» нет.
  Запрос слить этап (общий чат, «Продолжить» у этапа) вливает его принятые задачи
  по одной, сначала зависимости.
- **Слияние — операция Git.** Принятый результат вливается в базовую ветку
  стратегией проекта в служебном checkout. Кандидат интеграции, отдельное
  окружение, агент слияния и повторный прогон сохранённых проверок не
  используются. Запускаются только `checks` из настроек проекта, если они заданы.
  Код, слившийся без конфликта, отдельно не тестируется.
- **Конфликт возвращается задаче.** Задача переходит в «В работе», её агент в
  своём чате, checkout и окружении вливает базовую ветку, разрешает конфликт,
  проверяет затронутое и снова вызывает `submit_result`; после этого задача
  вливается. Внутри собственного `submit_result` агент получает это указание
  ответом инструмента, иначе — сообщением. Кнопки карточки «Обновить ветку» и
  «Разрешить агентом» делают то же по решению владельца. В одном проекте
  автослияние возвращает агентам по одному конфликту за раз: остальные задачи
  вливаются на уже обновлённую базу.
- **Старт на влитых зависимостях.** Не начатая задача ждёт, пока её зависимости
  не влиты (`done`); статус `review` зависимости старт больше не открывает.
  Подготовка зависимостей интеграцией остаётся только для задач, начатых раньше,
  и для задач, разблокированных владельцем вручную.
- **Зависимость публикации.** Задача вливается после своих зависимостей; сверка
  версии уже влитой зависимости не выполняется — расхождение решает слияние Git.
- **Ошибка слияния** (локальные правки в основной копии, упавшая проверка
  проекта, изменённая приёмка) сохраняется за задачей: карточка на доске
  показывает «слияние: ошибка», текст — в чате задачи.
- **Кандидаты, начатые до решения,** при старте Skaro не возобновляются и
  снимаются; публикуется только уже проверенный кандидат. Их задачи вливаются
  по одной.
- **Что видит владелец.** Карточка задачи на доске, строка списка и строка
  плана говорят о слиянии словами: «сливается сейчас», «в очереди слияния» и
  после какой задачи (невлитая зависимость либо задача, которая сливается или
  разрешает конфликт), «слияние: ошибка», у задачи в работе — «конфликт
  слияния, разрешает агент». При автослиянии принятая задача не считается в
  «ждут вас» и «Активных»: она ждёт Skaro, а не владельца. Без автослияния
  карточка остаётся «На ревью» и ждёт подтверждения в чате задачи.
- **Управление.** Слить задачу вручную вне очереди — перетащить карточку в
  «Готово» или подтвердить карточку в чате задачи. Остановить автослияние —
  переключатель «Вливать автоматически». Задача, агент которой остановился на
  конфликте, очередь не держит.

Проверено 12.10.2026 целевыми тестами на настоящих Git и SQLite, без агентов и
заглушек: слияние задач этапа по одной тремя стратегиями, оба чат-маршрута,
`submit_result` с автослиянием и конфликтом, передача конфликта агенту задачи,
проверки проекта при слиянии, отмена слияния одной задачи, старт только на
влитых зависимостях, публикация кандидата, начатого до решения. В работающем
приложении не проверено. Полный прогон не выполнялся.

## Данные и исполнение

`completion.<project>.result.<task>` сохраняет точный SHA принятого результата,
ветку, рабочий каталог, ревизию критериев и сообщение. Статус хранится только
в файле задачи; SQLite хранит факты выполнения, а не альтернативную доску.

`completion.<project>.operations` содержит область операции, входы, стратегию,
исходный SHA базы, проверенный кандидат и состояние. Кандидат защищён ref
`refs/skaro/completions/<operation>`. Проверки выполняются до публикации;
повторный запрос после успешной публикации не создаёт повторное слияние.

Служебный detached worktree объединяет принятые результаты. Источники агентов
не переписываются. Стратегия проекта применяется к общей операции: squash
создаёт один итоговый коммит, merge сохраняет исходную историю, rebase работает
только в служебном checkout. Сообщения задач входят в описание операции.
Изменения `.skaro/` из источников отбрасываются, актуальные файлы включённых
задач публикуются со статусом done. Локальные пользовательские правки основной
копии проверяются прежним механизмом безопасной публикации.

Новые независимые задачи запускаются параллельно. Зависимая задача получает
точные SHA принятых зависимостей перед запуском, независимо от этапов и их
отсутствия. Начатые ранее задачи в общем worktree сохраняют последовательность
до завершения; произвольное разделение
каталога с незавершённой работой запрещено. In-place также требует взаимного
исключения и уже влитых зависимостей.

Статус `review` снимает блокировку запуска для зависимостей внутри этапа,
между этапами и без этапа. До запуска агента Skaro проверяет актуальность
принятого результата и подключает его штатной интеграцией. Отсутствующий
результат, изменившаяся ветка или неразрешённый конфликт не обходятся.
Принятый результат зависимой задачи сохраняет точные SHA подключённых
зависимостей, включая унаследованные. Повторная подготовка сохраняет эти
данные и тогда, когда коммиты уже присутствуют в рабочей ветке.

Готовность запуска и разрешение публикации различаются: внешняя зависимость
должна быть уже опубликована либо входить в выбранную операцию слияния.
Skaro не расширяет область слияния на другие этапы автоматически. Если
зависимость представлена новым результатом после подключения, публикация
зависимой задачи требует повторной интеграции и сдачи результата. Проверка
повторяется перед публикацией; зависимость не переводится в `done` лишь
потому, что её код содержится в рабочей ветке другой задачи.

Конфликты подготовки и публикации проходят сохраняемую операцию интеграции
с автоматическим исполнителем, проверками и продолжением. Контракт окружения,
диагностики и восстановления: [integration-process.md](integration-process.md).

## Восстановление

Наблюдатель работает без открытого чата. Если проверенный кандидат уже входит
в базовую ветку, он завершает записи о слиянии и обновление статусов. При
внешнем merge/ff требуется доказанное вхождение сохранённого результата.
Изменённые критерии, новые незакоммиченные изменения и неизвестное переписывание
истории сохраняют задачу на ревью с объяснением, а не закрывают её по догадке.

Журнал публикации Git содержит исходные и ожидаемые файлы, индексы и владельца
блокировки. После смерти процесса восстановление возможно только при
совпадении ветки, SHA, файлов и индекса с журналом. При посторонних правках
журнал и пользовательские файлы сохраняются для разбора. Старые журналы без
данных владельца требуют ручного восстановления. Отменённые известные
слияния исключаются из восстановления по ancestry.

## Общий чат и CI

`merge_task` доступен задаче и общему чату. Общий чат обязан указать task_id
или milestone_id; import-сессия сливать не может. Задача ограничена собой и
своим этапом. partial разрешён для явной просьбы влить только готовые задачи.

`ci_run` принимает реальный ID GitHub Actions и kind ci/release. Репозиторий
проверяется по origin проекта; нужен установленный авторизованный `gh`.
Сохранённые запуски наблюдаются после окончания хода агента и перезапуска
приложения. Изменения состояния выводятся существующими системными сообщениями
в исходном чате. Общий контекст содержит состояния слияний и CI.

Автоматически повторяется только startup_failure и только один раз.
retry_failed — явное действие агента по поручению пользователя. Намерение
повтора сохраняется перед запросом GitHub; при неизвестном результате запроса
повтор не дублируется. Ошибки тестов не маскируются повторными запусками.
Успех workflow ещё не подтверждает установку релиза: агент проверяет
опубликованные артефакты. Ошибка релиза не отменяет завершение уже влитых задач.

## Проверки

Обязательные сценарии: автоматическое завершение этапа, оба типа чата,
внешний merge/ff, собственный squash, параллельные результаты и зависимости,
повторный запрос, перезапуск после публикации, сохранение локальных правок,
отмена слияния, возобновление наблюдения CI и отсутствие чата этапа.
Результаты фактически выполненных проверок указываются отдельно; этот список
не означает, что сценарии уже проверены.

отключения питания. Проверены групповая отмена всех стратегий, перезапуск
после опубликованной отмены, конфликты, незавершённые критерии, ошибки команд
проверки, изменение проверяемой конфигурации и сохранение staged/unstaged,
untracked и ignored данных. Закрытие приложения дожидается фоновой очистки
окружений перед закрытием SQLite.

запрос повторить успешный workflow отклонён до удалённого вызова. Сбойный

Неизвестный внешний squash оставляет review: это также проверенный сценарий,
а не попытка угадать соответствие переписанной истории.
