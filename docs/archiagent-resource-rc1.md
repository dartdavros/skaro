# RC-1 — реестр ресурсов и безопасная очистка

Дата: 11.11.2026. Этап [плана ресурсов](archiagent-resource-plan.md#rc-1--реестр-владение-и-диагностика-очистки).
Статус: **реализован и локально проверен**; результаты и ограничения ниже.
Основание рабочего дерева: `22f3d4fb0ec12c3cfd0e49d650869f1ee13175ea`.
Изменения ещё не закоммичены и не выпущены; установленный Skaro не обновлялся.

## Что изменено

SQLite AppDb получил миграцию v9: таблицы `resources` и `resource_outcomes`.
Реестр хранит точную идентичность, проект и владельца, назначение, сохранность,
потребителей, revision/generation, ссылки на источник/восстановление и исходы.
Для filesystem-ресурса идентичность — абсолютный путь, для окружения — точный
Compose project. Имя, префикс и наличие bind mount не выдают полномочия.

`DbResources` проверяет структуру и допустимые значения, отклоняет устаревшую
revision/generation и конфликт повторной регистрации. Повтор с тем же
operation ID возвращает тот же исход; другой payload с этим ID отклоняется.
Новая generation возможна только после освобождения предыдущей. Освобождённый
ресурс не может иметь потребителей. Классификация не меняется обычным update.
В исходах сохраняются коды причин, а не сырой вывод с потенциальными секретами.

Открытие AppDb вынесено в отдельный модуль. `AppDb.readOnly` не мигрирует старую
БД; отсутствие новых таблиц означает пустой ledger, а не создание схемы.
Инвентаризация разделена с записью наблюдений и не запускает окружения.

### Worktrees

Новый checkout задачи получает запись о владельце и назначении до создания. Повторное
использование проверяет репозиторий, канонический путь и ветку; неизвестный
существующий каталог не приобретает disposable-классификацию при открытии.

Инвентаризация сопоставляет управляемую область, реальные Git worktrees,
ветку/HEAD, записи запусков и читаемые метаданные задач. Очистка повторно читает
эти данные внутри существующей сериализации задач. Все владельцы общего
checkout должны быть `done`; очередь, агент, интеграция, review и льготный
срок после явного восстановления защищают ресурс от удаления.

Отдельные зарегистрированные ресурсы с пересекающимися путями защищают данные,
в том числе записи других проектов: читаются только записи ledger, без обхода
чужих каталогов. Перед удалением сохраняются ветка и точный commit для
восстановления; повторно проверяются ветка/HEAD и зависимости Docker mounts.

Существующие незакоммиченные исправления полного удаления завершённого checkout
сохранены. В разрешённую disposable-область входят ignored/untracked файлы;
это правило не переносится на незавершённые/review или неизвестные ресурсы.
Отсутствие метаданных и ошибка Docker удерживают checkout с причиной.

Ручное удаление задачи также проходит через ledger и прежнюю строгую проверку
изменённых/ignored/untracked файлов. Ошибка очистки окружения блокирует удаление
задачи, а точечное удаление checkout не вызывает общий `git worktree prune`.
Каталог интеграции проверяется по сохранённой операции, точному управляемому
пути, detached HEAD и сохранённому Git ref. Прежний fallback `rm` для каталога,
который Git уже не знает, исключён. Уникальные изменения кандидата удерживаются.

### Окружения

Существующие исполнители Docker используют общий guard перед start/stop/remove
и очисткой retired-остатков. Registry allocation, принадлежность задачи,
канонический checkout, точные Compose labels и рабочая директория сверяются
с ledger. Совпадение названия не является достаточным доказательством.

Объявленный источник данных проекта регистрируется как `project-dev/persistent`
отдельно от копии задачи. Во время подготовки копии он получает потребителя
`copy`, который освобождается в `finally`. Исчезновение потребителя не даёт
права удалить источник. Источники из registry и постоянные записи других
проектов также исключаются из области task cleanup.

Повреждённый registry не подменяется пустым списком и не перезаписывается.
Когда точная identity недостоверна, причина `registry_invalid` сохраняется
проектным событием. Для известных ресурсов retained/failed/stop/remove
сохраняются в ledger. Невозможность Docker inspect не считается успешной
очисткой; ошибка одного ресурса не разрешает удаление остальных без проверки.
Повторное появление объектов после `released` не присваивается прежнему
generation. Ошибка удаления служебных Compose-файлов после Docker cleanup
сохраняется отдельно и завершает фоновое задание с ошибкой.

идемпотентность operation ID, повторное открытие и read-only старой схемы.

fake backend или подменённого сервиса.

`pnpm install --frozen-lockfile` восстановил их из локального store, без изменения
manifest/lockfile и версий. Sandbox Vitest выдавал `ENOENT` на собственных
временных SSR transform-файлах: финальные целевые прогоны вне sandbox прошли.
Это ошибки проверочного окружения, а не успешные тесты; они не скрыты повтором.
Сборка завершилась с предупреждениями зависимостей Zod, Claude SDK и
web-tree-sitter; ошибок сборки нет. Версии зависимостей не менялись.

## Границы приёмки

Это базовый реестр и защитные проверки существующих исполнителей. Общего
admission по RAM/диску/CPU, heartbeat leases, политики кешей, полного recovery
и нового интерфейса событий здесь нет: это RC-2–RC-4 и AC-4.

Сохранённая неоднозначная legacy-запись остаётся удержанной даже после появления
дополнительных данных. Автоматическое изменение владельца/класса не разрешено;
явное принятие такого ресурса под управление требует отдельной реализации.
Уже доказанный registered-ресурс сохраняет классификацию при временном сбое
инспекции, но операция ждёт успешной актуальной сверки.
Временная недоступность доказательств до первой регистрации записывается
отдельной диагностикой и откладывает классификацию; это позволяет повторить
проверку после возвращения Docker/метаданных без автоматического повышения
сохранённого `unknown`. Доказанный конфликт владения остаётся блокирующим.

На Cat-pilot сейчас нет реального disposable окружения/checkout для удаления
и постоянного dev-источника для проверки копирования. Положительный сценарий
удаления, полный запуск/остановка, crash/restart приложения во время Docker
операции и измеренное освобождение диска/RAM не подтверждены этим отчётом.
Они остаются в приёмке RC-4; результат инвентаризации не заменяет их.
Сохранность исходов после повторного открытия проверяется на настоящем SQLite
с наблюдением реально существующего каталога, без наполнения проекта seed-данными.

UI не изменён; browser-проверка к RC-1 не относится. Полный suite и релиз
не выполняются в рамках этого этапа.
