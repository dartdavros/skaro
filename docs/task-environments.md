# Окружение задачи и сохранность данных

Слияние завершает агентскую сессию, сохраняет worktree и ветку и удаляет окружение
задачи (см. ниже). Игнорируемые файлы в worktree не попадают в Git и не
восстанавливаются из коммита. Повторный запуск использует существующий checkout,
проверяя репозиторий и ветку; чужой каталог не заменяется.

Удаление задачи предварительно проверяет все её worktree. Основная рабочая копия,
незарегистрированный каталог, изменённые, неотслеживаемые или игнорируемые файлы
блокируют удаление. Bind mounts существующих Docker-контейнеров блокируют его,
даже если контейнер остановлен. Недоступность Docker также блокирует удаление:
зависимости не удалось проверить. Ошибка не скрывается; принудительного удаления
worktree нет. Это консервативная защита, а не управление всеми процессами хоста.

## Окружение задачи — одноразовая копия (D-37)

У задачи в собственном worktree своё окружение: сервисы проекта на её исходниках и
копия данных основного окружения. В окружении задачи нет ничего уникального:
ценные данные живут только в основной рабочей копии. Поэтому окружение можно
остановить и удалить в любой момент без потерь, а задачи не мешают друг другу —
у каждой своя база, свой backend и свои образы.

Окружением владеет Skaro, а не агент:

- **Имя.** `skaro-<проект>-<задача>` — имя compose-проекта. Skaro передаёт его в
  shell агента (`COMPOSE_PROJECT_NAME`), поэтому всё, что агент запускает через
  Compose, попадает в окружение своей задачи.
- **Порты.** Skaro выдаёт свободные host-порты и хранит их за задачей до её
  удаления; агент порты не выбирает и override-файлы не пишет.
- **Запуск.** Агент вызывает инструмент `start_environment` MCP-сервера Skaro и
  получает адреса готовых сервисов. Окружения запускаются по одному.
- **Лимит.** Одновременно работает не больше окружений, чем задано настройкой
  «Одновременных запусков». Слот очереди занимает каждый ход агента. Окружения
  задач, чей агент работает, не трогаются; из остальных остаются последние по
  использованию, лишние останавливаются (`docker stop`, данные сохраняются).
- **Удаление.** При слиянии, удалении задачи и при старте Skaro для завершённых
  задач окружение удаляется целиком: контейнеры, сети, тома и собранные образы.
  Возврат задачи в «Не начата» только останавливает его.

Принадлежность контейнера задаче определяется по имени окружения (compose-проект),
а для запущенного под другим именем — по каталогу worktree задачи (каталог
compose-проекта или bind mount). Контейнер, запущенный агентом через `docker run`
без Compose и без монтирования worktree, Docker ничем не связывает с задачей:
такой контейнер Skaro не видит, поэтому агенту это запрещено инструкцией. Контейнеры основной копии и чужих
проектов Skaro не останавливает и не удаляет. Сети, тома и образы удаляются только
у compose-проектов, целиком принадлежащих задаче.

### Описание окружения в проекте

Раздел `environment` в `.skaro/config.yaml`. Команды выполняются в worktree задачи;
в значениях доступны `{name}`, `{root}` (основная копия), `{worktree}` и имена
переменных портов.

```yaml
environment:
  ports: [API_PORT, UI_PORT]            # каждой переменной — свободный порт
  env:                                   # переменные команд и shell агента
    COMPOSE_FILE: compose.yaml|{root}/compose.task.yaml
    APP_IMAGE: app:{name}                # свой тег образа на задачу
  create: ./scripts/clone-env.sh {name}  # копия данных, один раз на задачу
  start: docker compose up -d --wait     # запуск сервисов
  ready: http://localhost:{UI_PORT}/health   # 2xx = окружение готово
  urls:
    frontend: http://localhost:{UI_PORT}
```

`create` создаёт копию данных основного окружения в томах compose-проекта задачи.
Если копия удалена вручную, Skaro создаёт её заново и не запускает сервисы на
пустых данных. `COMPOSE_PROJECT_NAME` и `SKARO_ENV_NAME` проект не задаёт. Ошибка в разделе показывается как проблема `config.yaml`; окружение при
ней не запускается.

Без раздела `environment` агент поднимает сервисы штатными средствами проекта сам,
но под именем своей задачи; лимит, остановка при простое и удаление при слиянии
действуют так же. Задача без worktree работает с основным окружением как есть.

Изменения backend проверяются на исходниках своей задачи. Нельзя останавливать,
перенастраивать или заменять сервис другой задачи или основной копии. Если
окружение не запустилось, агент сообщает конкретный blocker; вопрос задаёт только
для отсутствующего решения владельца. Перед browser-проверкой проверяются frontend
и настоящий backend readiness, включая БД и Redis. Ответ frontend `200` и backend
liveness сами по себе не подтверждают рабочее окружение. Mock API, временные
серверы, seed-аккаунты и сброс учётных данных запрещены.

Полный доступ снимает подтверждения выполнения инструментов в пределах уже
разрешённой задачи; не отменяет ограничения владельца и не разрешает менять
чужое окружение. В остальных режимах разрешения запрашивает агентский runtime
своей карточкой. Агент не дублирует эти запросы текстом. Необходимые решения
владельца задаются через структурированный инструмент вопросов. Для Codex Skaro
включает `default_mode_request_user_input` только в своей сессии и передаёт
инструкции Default mode, разделяющие решения по задаче и разрешения инструментам.
Карточка вопроса появляется только после фактического вызова инструмента вопроса.
Текст о blocker и `submit_result` её не создают: агент должен вызвать инструмент,
дождаться необходимого ответа и не заявлять об отправке без успешного вызова.
Если инструмент недоступен или вызов завершился ошибкой, агент сообщает это явно.
В том же процессе Skaro передаёт `suppress_unstable_features_warning=true`, чтобы
штатное предупреждение об экспериментальных функциях не выглядело как сбой сервиса.
Пользовательский `config.toml` не меняется; ошибки и остальные предупреждения
runtime продолжают отображаться. Функция вопросов остаётся экспериментальной.

Каждая новая агентская сессия задачи получает официальный `@playwright/mcp`
через stdio, с отдельным временным профилем (`--isolated`) и установленным Chrome.
Скриншоты и трассы сохраняются в данных Skaro: `browsers/<run-id>/`.
Сервер не подключается к личному профилю и не требует расширения Chrome.
Если Chrome не установлен или реальный API недоступен, это blocker проверки.
Playwright не получает автоматического доверия: применяются разрешения агента.

Уже запущенные сессии и старая сборка Skaro не получают изменения автоматически.
Обновлённая сборка нужна для защиты жизненного цикла; новая/переподключённая
агентская сессия нужна для MCP браузера. Перезапуск не должен прерывать активные
задачи без решения владельца.
