# Окружение задачи и сохранность данных

Слияние завершает агентскую сессию, сохраняет worktree и ветку и удаляет окружение
задачи (см. ниже). Игнорируемые файлы в worktree не попадают в Git и не
восстанавливаются из коммита. Повторный запуск использует существующий checkout,
проверяя репозиторий и ветку; чужой каталог не заменяется.

Удаление задачи предварительно проверяет все её worktree. Основная рабочая копия,
незарегистрированный каталог, изменённые, неотслеживаемые или игнорируемые файлы
блокируют удаление. Bind mounts существующих Docker-контейнеров блокируют его,
даже если контейнер остановлен. Недоступность Docker также блокирует удаление:
зависимости не удалось проверить. Ошибка не скрывается; принудительного удаления
worktree нет. Это консервативная защита, а не управление всеми процессами хоста.

## Окружение задачи — одноразовая копия (D-37)

Перед отправкой сообщения агенту Skaro проверяет папку изолированного запуска, включая уже открытую сессию. Если worktree отсутствует или вместо папки находится файл, запуск блокируется до вызова агента. Основная рабочая копия не используется как запасной путь. Работа в ней разрешена только для запуска, изначально созданного без worktree (`in-place`). История удалённой задачи не восстанавливает ни сессию, ни окружение новой задачи.

У задачи в собственном worktree своё окружение: сервисы проекта на её исходниках и
копия данных основного окружения. В окружении задачи нет ничего уникального:
ценные данные живут только в основной рабочей копии. Остановка сохраняет копию
через разработку, ревью и исправления. Удаление потребует повторной подготовки
и не сохраняет состояние предыдущей проверки. Задачи не мешают друг другу —
у каждой своя база, свой backend и свои образы.

Новые задачи одного этапа получают собственные ветки, worktree и окружения
(D-40, заменяет D-38). Независимые задачи могут выполняться параллельно;
этап группирует задачи на плане, но не сокращает число окружений.
Сохранившиеся старые запуски в общем checkout этапа по-прежнему делят его
окружение и исполняются последовательно. Новые общие checkout этапов не создаются.

Создание worktree не запускает сервисы автоматически: агент вызывает
`start_environment`, когда проверке нужны работающие сервисы. Первая подготовка
может включать сборку образов и копирование данных; повторный запуск сохраняет
копию данных, пока окружение не удалено. Поэтому небольшая связанная работа
должна оставаться одной задачей вместе с её тестами и документацией, а не
порождать отдельные окружения на каждый шаг. Правила декомпозиции описаны в
[планировании проекта](project-planning.md#границы-задач).

Окружением владеет Skaro, а не агент:

- **Имя.** `skaro-<проект>-<задача>` — имя compose-проекта. Skaro передаёт его в
  shell агента (`COMPOSE_PROJECT_NAME`), поэтому всё, что агент запускает через
  Compose, попадает в окружение своей задачи.
- **Порты.** Skaro выдаёт свободные host-порты и хранит их за задачей до её
  удаления; агент порты не выбирает и override-файлы не пишет. Если назначенный
  порт после остановки занял чужой процесс или запретила ОС, Skaro перед запуском
  выделяет замену и сохраняет её. Порты своих работающих контейнеров сохраняются.
  Перед запуском Skaro читает итоговую Compose-конфигурацию и оставляет только выделенные им
  публикации, привязанные к `127.0.0.1`. Остальные сервисы доступны внутри
  Compose-сети и через `docker compose exec`, без host-порта.
- **Запуск.** Агент вызывает инструмент `start_environment` MCP-сервера Skaro и
  получает адреса готовых сервисов. Окружения запускаются по одному.
- **Настройка.** Если для порученной проверки нужен документированный сервис,
  отсутствующий в команде запуска, агент сам меняет команду через
  `configure_environment`, затем вызывает `start_environment` и проверяет сервис.
  Владелец не должен вручную редактировать настройки ради выполнения задачи.
- **Время жизни.** Окружение работает, пока его задачей владеет активный ход
  агента, исполнитель проверки интеграции или ручной просмотр. Каждый владелец занимает слот очереди
  «Одновременных запусков»; свободные слоты не удерживают старые сервисы.
  После освобождения слота все простаивающие окружения останавливаются
  (`docker stop`, данные сохраняются). Та же проверка выполняется при старте
  Skaro; при выходе останавливаются все принадлежащие ему сервисы. Основная
  копия проекта и чужие Compose-проекты не затрагиваются.
- **Ручной просмотр.** Клик по ссылке своего окружения в ленте задачи ставит его
  запуск в ту же очередь. Существующий Banner над лентой показывает ожидание,
  запуск или готовый просмотр; «Завершить просмотр» освобождает слот и
  останавливает сервисы с сохранением данных. Открытие чата само по себе ничего
  не запускает. Переход в системный браузер, другая задача или другой этап не
  завершают просмотр. Агент этой задачи ждёт окончания просмотра, чтобы не менять
  проверяемую рабочую копию; независимые задачи продолжают занимать свободные слоты.
  При старте перечитываются актуальные настройки; старые ссылки используют новый
  порт, если прежний занят. Произвольные внешние ссылки не запускают окружение.
  Незавершённый просмотр после перезапуска закрывается: Skaro останавливает
  зарегистрированные процессы подготовки и сервисы, сохраняя данные задачи.
- **Удаление.** При слиянии, удалении задачи и при старте Skaro для завершённых
  задач окружение удаляется целиком: контейнеры, сети, тома и собранные образы.
  Возврат задачи в «Не начата» только останавливает его.

Статус «На ревью» не является основанием для удаления. Остановленные контейнеры
и тома этой задачи позволяют исправлять результат без нового клонирования БД.
Число одновременно используемых окружений ограничено слотами, а число сохранённых
копий данных зависит от незавершённых задач. Сервисы и изменяемые данные разных
задач не переиспользуются между ними; кеш слоёв Docker работает независимо.

Перед удалением необходимо доказать завершение владельца и читаемость актуальных
метаданных. Ошибка чтения задачи не означает её удаление. Неудачная очистка
перед первичным созданием блокирует новое копирование, а не продолжает его поверх
остатков. Снятие проекта со списка Skaro не является удалением его данных.

Принадлежность контейнера задаче определяется по имени окружения (compose-проект),
а для запущенного под другим именем — по каталогу worktree задачи (каталог
compose-проекта или bind mount). Контейнер, запущенный агентом через `docker run`
без Compose и без монтирования worktree, Docker ничем не связывает с задачей:
такой контейнер Skaro не видит, поэтому агенту это запрещено инструкцией. Контейнеры основной копии и чужих
проектов Skaro не останавливает и не удаляет. Сети, тома и образы удаляются только
у compose-проектов, целиком принадлежащих задаче.

### Описание окружения в проекте

Раздел `environment` в `.skaro/config.yaml`. Команды выполняются в worktree задачи;
в значениях доступны `{name}`, `{root}` (основная копия), `{worktree}` и имена
переменных портов.

```yaml
environment:
  ports: [API_PORT, UI_PORT]            # каждой переменной — свободный порт
  env:                                   # переменные команд и shell агента
    COMPOSE_FILE: compose.yaml|{root}/compose.task.yaml
    APP_IMAGE: app:{name}                # свой тег образа на задачу
  create: ./scripts/clone-env.sh {name}  # копия данных, один раз на задачу
  start: docker compose up -d --wait     # запуск сервисов
  ready: http://localhost:{UI_PORT}/health   # 2xx = окружение готово
  urls:
    frontend: http://localhost:{UI_PORT}
```

`create` создаёт копию данных основного окружения в томах compose-проекта задачи.
Если для копирования нужны сервисы основной копии, `environment.source`
содержит `project` (Compose-проект) и `services` (имена сервисов). Агент может
сохранить эту декларацию для задачи через `configure_environment` с `source`
и `expected_source` (текущая декларация либо `null`). Перед первым копированием
Skaro проверяет принадлежность всех существующих контейнеров основной рабочей
копии, запускает только остановленные объявленные контейнеры и ждёт их health.
Контейнеры источника не создаются, не пересоздаются, не перенастраиваются и
не включаются в остановку/удаление окружений задач. Их тома, mounts, образы,
учётные данные и содержимое не подменяются. Отсутствующий или чужой контейнер
останавливает подготовку до создания копии. Это согласованная 31.10.2026
подготовка штатного источника, а не разрешение менять общие сервисы агентом.

Если копия удалена вручную, Skaro создаёт её заново и не запускает сервисы на
пустых данных. `COMPOSE_PROJECT_NAME` и `SKARO_ENV_NAME` проект не задаёт. Ошибка в разделе показывается как проблема `config.yaml`; окружение при
ней не запускается.

`start` выполняется при каждом запросе сервисов и отвечает за актуальность именно
этой рабочей копии: сборку изменившихся образов/зависимостей, запуск нужных процессов
и штатные миграции проекта. Один `docker compose up` не заменяет миграции и не
доказывает обновление всех процессов. Skaro не подменяет проектную команду своей.
После изменения исходников агент повторяет `start_environment` и значимые проверки;
успех прежней версии не доказывает корректность новой. Изменение другой задачи
не обновляет файлы и данные текущей. С 12.10.2026 (D-45) отдельного окружения
для слияния нет: задача вливается операцией Git, а конфликт её агент разрешает в
окружении самой задачи, см. [completion-process.md](completion-process.md).

Последний реальный запуск хранит в записи окружения `lastStart`: время ожидания
очереди Docker, подготовки, копирования (`create`), запуска и readiness, факт
повторного использования данных и ошибку при неудаче. Эти измерения позволяют
отличать дорогую сборку от копирования данных и ожидания сервисов. При повторном
использовании данных команда `create` не вызывается. История измерений не растёт
бесконечно — хранится только последний запуск каждого окружения.

Проверка 08.10.2026 прошла в настоящем Electron на существующих окружениях
Chatballs T-055 (M11) и T-062 (M13), с изолированной SQLite Skaro и реальными
worktree, Compose-сервисами и томами. Проверены очередь при одном слоте,
одновременный просмотр при двух, завершение просмотра, отмена запуска и
восстановление после аварийного выхода Electron. После проверки сервисы
остановлены; состав и идентичность томов сохранены, Git-ссылки и файлы задач
исходного проекта не изменились. Баннер сверён в состояниях очереди, запуска,
просмотра и после закрытия. Mock API и подмена сервисов не использовались.

На последнем повторном запуске T-055 копирование заняло `0 мс` (`reusedData: true`),
подготовка — `2377 мс`, проектная команда запуска — `38299 мс`, readiness —
`2517 мс`. Повторное копирование данных не выполнялось; сборка и запуск сервисов
по-прежнему требуют времени. Опциональный сценарий
`e2e/environment-review-live.spec.ts` запускается с `SKARO_LIVE_PROFILE`,
`SKARO_LIVE_TASKS` (две существующие задачи) и `SKARO_AGENTS_DIR`; проверка
требует закрытого основного Skaro и остановленных окружений этих задач.

### Изменение команды запуска агентом

`configure_environment` без аргументов возвращает текущее описание окружения.
Для изменения агент передаёт `start` (полную новую команду) и `expected_start`
(прочитанную текущую команду). Если команда уже изменилась, запись отклоняется:
агент перечитывает её, чтобы не потерять чужое изменение. Пустая команда и
неизвестные переменные шаблона отклоняются той же проверкой, что и config.yaml.

Skaro хранит новую команду в записи конкретного окружения в своей БД. Настройка
сохраняется при остановке, перезапуске приложения и смене агентской сессии;
удаление окружения удаляет её. Для исторического общего checkout этапа команду
разделяют использующие его задачи. Основной config.yaml и остальные окружения
не меняются. Имя, копирование данных, переменные и readiness задаются проектом
как прежде. Для документированного доступа с host агент дополнительно передаёт
`ports` (имена переменных, без номеров) и `expected_ports` (прочитанный полный
список). Инструмент добавляет объявления к существующим и выделяет свободные
порты; несогласованное изменение отклоняется до сохранения. Дополнительные
объявления также сохраняются за окружением и не меняют остальные задачи.

Тестовому/admin backend, используемому через `exec`, host-порт не нужен.
Отсутствующая в `environment.ports` публикация, например стандартный `18001`,
удаляется из конфигурации окружения автоматически. Агенту не требуется менять
порт в команде, выбирать `0` или спрашивать разрешение на рутинную настройку.

Skaro хранит свой Compose override в `environments/<имя>/ports.yaml` внутри
данных приложения и передаёт его через `COMPOSE_FILE` командам и shell агента.
Рядом хранится `ports.env` только с назначенными номерами портов. Стабильный
`COMPOSE_ENV_FILES` позволяет уже подключённому shell прочитать новые портовые
переменные, добавленные инструментом; существующие env-файлы проекта сохраняются
в списке. Для HTTP/browser-проверки агент использует актуальные адреса из
`start_environment`, поскольку старые переменные процесса не обновляются на месте.
Исходные Compose-файлы проекта не изменяются. Списки портов заменяются целиком
через `!override`, после чего Skaro повторно читает итоговую конфигурацию и
проверяет отсутствие невыделенных публикаций. Эта проверка выполняется до
`create`, поскольку копирование данных само может запускать Compose-сервисы.
Обычный merge списков не подходит: он сохранил бы старый конфликтующий порт.
Требуется Compose с поддержкой `!override` (2.24.4 или новее;
[правила объединения Docker Compose](https://docs.docker.com/reference/compose-file/merge/)).
Неподдерживаемая или ошибочная конфигурация блокирует запуск с диагностикой.
Правило регулирует публикации `ports`; сервисы с `network_mode: host` не
получают сетевую изоляцию этим механизмом.

Проверка 07.10.2026 выполнена на настоящих зарегистрированных окружениях
Chatballs T-062 и T-055 с их существующими копиями данных. Два `backend-admin`
работали одновременно без host-публикации `18001`; в обоих прошли HTTP-запрос
к admin и соединения с PostgreSQL и Redis через `exec`. После проверки
окружения остановлены, данные сохранены; основное окружение не менялось.
Автоматическая замена занятого порта, сохранность портовых объявлений и
передача новых переменных уже подключённому shell покрыты целевыми тестами.

Настройка и запуск выполняются последовательно в общей очереди окружений.
Успешная настройка ещё не означает запуск сервисов: агент обязан вызвать
`start_environment`, проверить нужный сервис через `docker compose ps/exec` и
выполнить требуемые тесты. Общая readiness не доказывает готовность отдельного
сервиса для проверки. Инструмент доступен только текущей сессии задачи; во время
смены агента вызов отклоняется. Ограничения владельца продолжают действовать.

Рутинное добавление предусмотренного проектом сервиса выполняет агент в рамках
поручения. Если требуется отдельное решение владельца, варианты вопроса описывают
действия агента. Получив решение, агент выполняет его инструментами, а не ждёт
ручной правки от владельца и не считает выбранный ответ подтверждением запуска.

Без раздела `environment` агент поднимает сервисы штатными средствами проекта сам,
но под именем своей задачи; лимит, остановка при простое и удаление при слиянии
действуют так же. Задача без worktree работает с основным окружением как есть.

Изменения backend проверяются на исходниках своей задачи. Нельзя останавливать,
перенастраивать или заменять сервис другой задачи или основной копии. Если
окружение не запустилось, агент сообщает конкретный blocker; вопрос задаёт только
для отсутствующего решения владельца. Перед browser-проверкой проверяются frontend
и настоящий backend readiness, включая БД и Redis. Ответ frontend `200` и backend
liveness сами по себе не подтверждают рабочее окружение. Mock API, временные
серверы, seed-аккаунты и сброс учётных данных запрещены.

Полный доступ снимает подтверждения выполнения инструментов в пределах уже
разрешённой задачи; не отменяет ограничения владельца и не разрешает менять
чужое окружение. В остальных режимах разрешения запрашивает агентский runtime
своей карточкой. Агент не дублирует эти запросы текстом. Необходимые решения
владельца задаются через структурированный инструмент вопросов. Для Codex Skaro
включает `default_mode_request_user_input` только в своей сессии и передаёт
инструкции Default mode, разделяющие решения по задаче и разрешения инструментам.
Карточка вопроса появляется только после фактического вызова инструмента вопроса.
Текст о blocker и `submit_result` её не создают: агент должен вызвать инструмент,
дождаться необходимого ответа и не заявлять об отправке без успешного вызова.
Если инструмент недоступен или вызов завершился ошибкой, агент сообщает это явно.
В том же процессе Skaro передаёт `suppress_unstable_features_warning=true`, чтобы
штатное предупреждение об экспериментальных функциях не выглядело как сбой сервиса.
Пользовательский `config.toml` не меняется; ошибки и остальные предупреждения
runtime продолжают отображаться. Функция вопросов остаётся экспериментальной.

Каждая новая агентская сессия задачи получает официальный `@playwright/mcp`
через stdio, с отдельным временным профилем (`--isolated`) и установленным Chrome.
Скриншоты и трассы сохраняются в данных Skaro: `browsers/<run-id>/`.
Сервер не подключается к личному профилю и не требует расширения Chrome.
Если Chrome не установлен или реальный API недоступен, это blocker проверки.
Playwright не получает автоматического доверия: применяются разрешения агента.

Уже запущенные сессии и старая сборка Skaro не получают изменения автоматически.
Обновлённая сборка нужна для защиты жизненного цикла; новая/переподключённая
агентская сессия нужна для MCP браузера. Перезапуск не должен прерывать активные
задачи без решения владельца.
