Статус: **реализован и локально проверен**; границы приёмки указаны ниже.
Исходная ревизия: `22f3d4fb0ec12c3cfd0e49d650869f1ee13175ea`.
Изменения RC-1 сохранены. Коммит, релиз и обновление установленного Skaro

## Что входит в этап

AC-1 добавляет механический контроллер входящих проектных операций: сохраняет
причину действия, проверяет допуск, фиксирует единственного исполнителя и исход.
Существующие task/chat/integration handlers остаются исполнителями. Отдельный
shell workflow, новая модель или новый агентный turn для этих переходов не нужны.

Одна запись `ProjectCoordinator` принадлежит проекту и не зависит от чата,
выбранной модели или срока жизни процесса. Это основа последующих этапов,
а не готовая общая память всех чатов или автоматический переговорщик работников.

Точки входа: `ProjectCoordinators`, `OwnerCommandCoordination`,
`coordinatedSessionHandlers`, `coordinatedTools` и `dispatchProjectOperation`.
Они используют прежние доменные проверки, сериализацию задач, разрешения,
историю, сервисы Git/Docker и ресурсный ledger RC-1.

## Долговечные записи

Миграция AppDb v10 добавляет `project_coordinators`, `coordination_events`,
`coordination_intents`, `coordination_operations` и `coordination_entities`.
Миграция v9 и ресурсные записи RC-1 не переопределяются. `AppDb.readOnly`
не мигрирует старую БД; чтение ещё отсутствующего контроллера возвращает пустой
результат. Удаление проекта не каскадирует незавершённые операции и доказательства.

Публичный вход — `db.coordination`. Запись содержит project/source/subject,
связь event → intent → operation, стабильные ID, idempotency key, режим,
scope key, hash входов, revision, время, состояние и свидетельство результата.
В журнал не копируются аргументы инструментов, сообщения, ответы с секретами
или сырой текст исключений. Evidence содержит код, локальные ссылки и digest.
Исходные данные остаются в существующих хранилищах со своими правилами доступа.

Приём event/intent/operation атомарен. Повтор точного запроса возвращает ту же
запись; изменённое содержимое с прежним ID отклоняется. У одного actionable
event/intent одна operation. Последующие действия получают собственные события
с причинной ссылкой. Незавершённая запись не превращается в новое право доступа.

Decision и blocker уже имеют типизированные сохраняемые метаданные, revision,
проверяемое evidence и переход из pending/open в конечное состояние через CAS.
Это не подключение трёх режимов прав, автоматического разрешения инцидентов
или глобального окна решений: они остаются в AC-3/AC-4. Ответ на такую запись
сам по себе не возобновляет остановленную задачу и не запускает операцию.

## Допуск и выполнение

Порядок: прочитать состояние → проверить актуальный доступ → атомарно получить
claim → вызвать существующий handler → сохранить фактический исход.
После ожидания очереди повторно проверяется runtime admission/живой HTTP grant.
Callback проверки доступа не сохраняется в БД. До вызова handler уже существует
durable claim; повторный claim даже с прежним claim ID не даёт второй запуск.

Режимы `mutation`, `delivery`, `control`, `observation` разделяют назначение
операции. Очередь и сохранённый scope owner исключают одновременный dispatch
конфликтующих действий. Доставка сообщений и управление работником отделены
от мутаций проекта; транзакция SQLite не удерживается на время handler или turn.

`projectVersion` — счётчик допущенных намерений типа `mutation`, а не версия
Git HEAD, файлов, окружения или всех внутренних изменений проекта. Mutation
обязательно содержит `expectedVersion`; устаревшее намерение получает durable
`rejected` с причиной `stale_project_version`. Другие режимы не увеличивают
этот счётчик; явно переданная ожидаемая версия всё равно проверяется.

Прежние доменные locks и проверки версий продолжают защищать исполнителей.
Внутренняя работа scheduler/recovery не становится вторым shell workflow.
Контроллер AC-1 не объявляет каждую фоновую запись или внешнее редактирование
файла своей транзакцией. Полные снимки требований/HEAD/окружения, инвалидирование
контекста и сверка перед возобновлением относятся к AC-2.

## Повторная доставка и исходы

Состояния operation: `queued → dispatching → succeeded | failed | uncertain`;
отклонённый до эффекта запрос получает `rejected`. Все изменения используют
revision/CAS. Неизвестный исход не переводится обратно в queued.

- `succeeded` означает полученное успешное завершение handler. Повтор MCP-запроса
  возвращает проекцию сохранённого receipt; первоначальный handler не вызывается.
  Это не копия прежнего текста ответа и не обещание неизменности текущего проекта.
- `failed` означает полученный конечный ответ handler с ошибкой. Он может иметь
  частичные эффекты; этот статус не утверждает rollback или отсутствие изменений.
  Тот же ID не исполняется повторно. Новая операция проходит обычные проверки.
- `uncertain` означает оборванный dispatch или отсутствие достоверного исхода.
  Scope остаётся удержанным до сверки. Исключение не считается разрешением
  автоматически повторить потенциально выполненное внешнее действие.
- `rejected` сохраняет причину недопуска и не вызывает handler.

Owner inbox сохраняет прежние command ID и аргументы. MCP получает идентичность
из доверенного grant + JSON-RPC ID либо admission generation + tool call ID.
Числовой и строковый JSON-RPC ID различаются; токен grant в журнал не попадает.

У общего IPC нет универсального retry envelope: новый вызов обычно получает
свежий ID. Два клика владельца не объявляются одним событием только по совпадению
параметров. Стабильный ID существующего сообщения/создания чата используется там,
где он уже передаётся. Дедупликация AC-1 гарантирует один эффект для одного ID,
а не распознавание любого похожего действия пользователя.

## Восстановление и границы

Recovery вызывается один раз при запуске singleton host до доставки команд
и фонового восстановления. Начатый dispatch без конечной записи становится
uncertain. Проверочный запуск ограничен зарегистрированным Cat-pilot через
`db.shell.projectScope`; чужие проекты не обходятся и не восстанавливаются.

Поддержанная сверка owner delivery использует сохранённое доказательство
приёма команды, не повторную отправку сообщения. Для подтверждённой остановки
чата и встроенного task runtime захватываются точные отменённые command ID.
После штатного проверенного teardown контроллер ждёт завершения этих доставок
до 15 секунд и может завершить их uncertain-операции как failed с evidence
команды и chat stop request/run epoch. Это не утверждает отсутствие частичного
эффекта и не отправляет команду повторно. Один флаг cancelled не служит proof.

Обычное interrupt-подтверждение legacy task без доказательства завершения
транспорта не снимает uncertain. Task-stop proof также не выдаётся участнику
интеграции, пока её операция не стала applied/stale. Неизвестный исход стороннего handler без
достоверного доменного адаптера также остаётся удержанным. Универсальный
автоматический reconcile внешних действий этим этапом не реализован.
Команда остановки имеет отдельный приоритетный scope и не ждёт решения
неоднозначного ответа на вопрос того же работника; доменная остановка сохраняет
свои проверки текущего runtime.

При завершении приложения новые действия перестают допускаться до закрытия
исполнителей; принятые, но ещё не отправленные сообщения сохраняются для
штатного восстановления inbox. Смена модели, закрытие окна или ошибка доставки
не создают новую логическую идентичность координатора.

На момент приёмки AC-1 этапы AC-2–AC-5 оставались открыты (актуальная приёмка
[AC-2 от 12.11.2026](archiagent-coordination-ac2.md) приведена отдельно): чаты ещё не были объединены общей версионированной памятью,
межзадачные блокеры не получили полный цикл policy/делегирования, проектного окна
решений и durable-проекции фоновой модалки нет. Resource admission/leases — RC-2,
новый порядок C4 — отдельные C4-1–C4-3. UI baseline в AC-1 не изменён.

Core-тесты читают фактический `package.json` и наблюдают существующий каталог,
а затем проверяют настоящий SQLite в изолированной БД. Проекты не наполняются
seed-данными. Проверены два соединения, повторное открытие, атомарный отказ,
устаревшая revision/project version, запрет повторного claim, scope с uncertain
операцией, независимый control и сохранение метаданных решений без resume.
Проверка старой схемы не вставляет строки проектов или ресурсов.
Dispatcher проверен настоящими чтениями файлов и ресурсным ledger: гонка двух
доставок, отозванный preflight, удержание queued при shutdown, конечный failed
receipt при ошибке filesystem и повторное открытие между эффектом и receipt.
Последний сценарий требует сверки реального resource outcome и не повторяет эффект.

Sandbox Vitest снова выдавал `ENOENT` на своих временных SSR transform-файлах;
точечные core-тесты вне sandbox прошли. Неудачный запуск не считается проверкой.
Mock API, fake backend, fixture worktrees и временные HTTP-серверы не создавались.

Read-only проверка Cat-pilot не запускает `createServices`, model turn, recovery,
Docker lifecycle или миграцию установленного профиля. Она не доказывает живой
crash/restart в момент внешнего эффекта. Полный workflow с агентами, проверка UI,
межпроектная конкуренция ресурсов и сквозная приёмка AG-1 здесь не выполнены.
Живой stop/resume во время native attach/send также не воспроизводился;
unit-проверка stop guard не объявляется проверкой завершения реального процесса.
Полный suite и релиз в рамках AC-1 не выполняются.
