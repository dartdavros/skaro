# ADR-0048: несколько аккаунтов Codex и автоматическое переключение

- Статус: целевой продуктовый сценарий задан владельцем; техническая схема
  продолжения сессии требует проверки. Реализация и живая приёмка не начаты.
- Дата: 02.11.2026.
- Основание: поручение владельца описать несколько аккаунтов Codex с общими
  настройками и автоматическим продолжением задачи при исчерпании лимита.
- Уточняет D-05, D-23 и [ADR-0046](0046-agent-registry.md).
- Не меняет архитектуру встроенного агента из [ADR-0047](0047-builtin-agent.md).
- Порядок работ и приёмки: [план реализации](../codex-multi-account-plan.md).

## Контекст

Пользователи имеют несколько собственных аккаунтов ChatGPT для работы с Codex.
Основной сценарий, указанный владельцем, — два аккаунта Pro или два Plus
с одинаковым доступом к моделям. Пять и более аккаунтов также допустимы;
искусственного ограничения количества в Skaro не вводим.

Сейчас `AgentManager` хранит один адаптер, статус и ревизию авторизации на
`AgentId`. В IPC, чатах и запусках выбирается тип агента, отдельного аккаунта нет.
При этом адаптер Codex уже принимает `codexHome`, передаёт `CODEX_HOME`
дочернему процессу и умеет заменять процесс с восстановлением нативной сессии
после изменения авторизации. Автоматической ротации аккаунтов в коде нет.

Обычный выбор аккаунта для новой задачи недостаточен: владелец хочет продолжать
одну задачу без ручного выбора, повторного входа и команды «продолжи».

## Решение

### Один агент и пул аккаунтов

В реестре остаётся единственный `AgentId = codex`, одна установка закреплённого
CLI и один набор общих настроек. Аккаунты — внутренние подключения этого
агента, а не новые регистрации `codex-1`, `codex-2` и не новые типы моделей.
Пользователь не выбирает аккаунт в задаче, чате или workflow.

Каждое подключение имеет устойчивый внутренний ID, подтверждённую Codex
идентичность, собственное состояние авторизации и снимок лимитов с временем
получения. Повторный вход в тот же аккаунт не создаёт дополнительную квоту
и не добавляет его второй раз в очередь переключения.

Авторизация выполняется штатным браузерным входом Codex для каждого аккаунта.
Пароли и токены не передаются в renderer, журналы, документы или IPC.
Жизненным циклом credentials управляет Codex; Skaro хранит только метаданные
и ссылку на изолированное хранилище. Ревизии авторизации разделены по аккаунтам:
добавление аккаунта не прерывает работающие сессии остальных.

Существующий вход пользователя сохраняется как исходное подключение.
Миграция не выполняет logout и не перезаписывает авторизацию внешнего CLI/IDE.
Способ подключения исходного профиля без конкурирующих копий refresh-токенов
входит в техническую проверку ниже.

### Общие настройки

Модель по умолчанию, effort, инструкции, MCP, skills, hooks и остальные
пользовательские настройки Codex имеют единый источник. Пользователь не
настраивает каждый аккаунт отдельно. Проектные overrides и текущие права
задачи сохраняются при переключении.

Изолированные каталоги авторизации не становятся независимо редактируемыми
копиями настроек. Применение общей конфигурации к процессам — ответственность
адаптера Codex; host не копирует произвольно содержимое `~/.codex`.
Общие настройки MCP не означают общую авторизацию внешних сервисов:
доступность необходимых подключений проверяется при продолжении.

Основной сценарий не требует дополнительных действий для выбора модели:
доступ у добавленных аккаунтов предполагается одинаковым. Защитная проверка
фактической совместимости сохраняется. Аккаунт без выбранной модели не
используется; молча менять модель, effort или права задачи нельзя.

### Выбор аккаунта и исчерпание лимита

Аккаунт назначается автоматически при запуске. Пока он доступен, работающая
сессия сохраняет его. При переключении кандидаты рассматриваются в устойчивом
порядке добавления; уже отклонённый аккаунт не проверяется бесконечно в рамках
одной попытки продолжения. Несколько сессий могут использовать один аккаунт.

Основание для переключения — подтверждённое исчерпание квоты аккаунта по
данным Codex, а не любое сообщение об ошибке и не приблизительный процент.
Сетевые сбои, отказ политики, переполнение контекста, бюджет задачи/сессии
и обычный кратковременный rate limit обрабатываются своими механизмами.
Текущей общей категории `limit` недостаточно: она объединяет
`usageLimitExceeded`, `rateLimitExceeded` и `sessionBudgetExceeded`.
Решение о ротации должно учитывать нативную причину и сведения о квоте.

Порядок автоматического продолжения:

1. Зафиксировать исчерпание квоты и состояние прерванного хода.
2. Исключить одновременную запись старого и нового исполнителя в одну сессию;
   подтвердить завершение или безопасную остановку прежнего хода и инструментов.
3. Выбрать авторизованный совместимый аккаунт, не отмеченный как исчерпанный.
   Отсутствие снимка лимитов означает неизвестность, а не полный остаток.
4. Восстановить нативный контекст и продолжить работу с сохранёнными настройками,
   историей, файлами и состоянием workflow, без сообщения от имени пользователя.
5. После успешного перехода записать одно служебное событие переключения.

Если следующий аккаунт тоже исчерпан, рассматривается следующий кандидат.
Когда доступных аккаунтов нет, работа останавливается с существующей обработкой
лимита; повторные попытки не образуют цикл. После времени сброса квота проверяется
заново: само наступление времени не считается подтверждением её восстановления.

Пул общий для всех задач и чатов пользователя. Исчерпание аккаунта становится
известно всем потребителям, но не вызывает массового перезапуска активных ходов.
Выбор кандидата и обновление состояния согласуются между main и workers.
Удаление либо повторный вход не позволяют применить устаревший результат выбора.

### Сохранение задачи и контекста

Переключение аккаунта сохраняет логическую сессию Skaro, тип агента, выбранную
модель, ветку, worktree, окружение, историю и критерии задачи. Оно не вызывает
коммит, слияние, сброс файлов или повторное выполнение завершённых действий.
Это не ручная смена типа агента из [D-39](../agent-handoff.md).
Смена credentials внутри Codex не должна подменяться новым пустым разговором.

Приоритет — штатное продолжение нативной сессии с её полным сохранённым
контекстом. Выжимка истории, текстовый replay и повторная отправка исходного
поручения не считаются эквивалентной реализацией и не используются как обход.
Если безопасное восстановление невозможно, продолжение блокируется с причиной.

Завершённые вызовы инструментов и их результаты сохраняются. При неоднозначном
исходе команды сначала устанавливается фактическое состояние; слепой повтор
операции с побочными эффектами запрещён. Нативные RPC-разрешения старого процесса
не переносятся как разрешения новому. Вопросы владельцу и карточки Skaro остаются
согласованными с историей; переключение не отвечает на них автоматически.

Переход журналируется с ID сессии, старого/нового подключения и стадией,
без credentials. После аварии восстанавливается незавершённый переход,
а не запускаются два исполнителя. Метаданные фактически использованного аккаунта
хранятся по сегментам исполнения, поскольку в одной задаче аккаунт может меняться.

### Интерфейс

Согласованные владельцем изменения текущего baseline:

- В «Настройки → Агенты → Codex» под сообщением о выполненном входе добавить
  действие «Войти ещё в один аккаунт». Добавление не заменяет прежний вход.
- Настройки остаются общими; отдельного выбора аккаунта в задаче/чате нет.
- В левом блоке «Оставшийся лимит» доступны сведения по аккаунтам. Только здесь,
  помимо управления входом в настройках, пользователю нужна детализация аккаунтов.
- Успешное переключение отражается в той же ленте и в том же визуальном стиле,
  что «Контекст сжат», без новой карточки, панели, иконки или анимации.

Точный текст служебного сообщения, вид нескольких аккаунтов в настройках,
компоновка лимитов и действия отключения/повторного входа ещё не заданы.
Для них требуется решение владельца до соответствующих UI-правок; этот ADR
не разрешает придумать отсутствующие элементы. Проценты разных аккаунтов
не складываются в фиктивный общий процент, неизвестный остаток не рисуется как 100%.

Событие переключения сохраняется и воспроизводится из истории ровно один раз.
Неуспешная попытка входа или восстановления не показывается как успешный переход.
Остальной [UI baseline](../ui-baseline.md) и [контракт ленты](../agent-output.md)
сохраняются.

## Техническая проверка перед реализацией ротации

Документация Codex описывает `CODEX_HOME`, варианты хранения credentials,
`account/login/start`, `account/read`, `account/rateLimits/read` и `thread/resume`.
Это основа решения, но не доказательство сохранения контекста при смене аккаунта.
Документация может опережать закреплённую версию; проверять нужно именно её.
На дату ADR в Skaro закреплён Codex 0.159.2.

До реализации автоматического переключения требуется доказать:

1. Независимость входов и обновления токенов, включая OS credential store;
   один `CODEX_HOME` на аккаунт сам по себе не доказывает изоляцию keyring.
2. Сохранение общего источника настроек при изоляции авторизации и отсутствие
   вмешательства в исходный внешний профиль пользователя.
3. Штатное восстановление одной нативной истории под другим аккаунтом без
   потери контекста, результатов инструментов, вложений и состояния дочерних агентов.
4. Безопасное продолжение после исчерпания квоты в середине выполнения,
   при параллельных задачах и после аварии между стадиями переключения.
5. Достоверное различение исчерпания квоты, временного rate limit и бюджета
   сессии на реальном протоколе закреплённой версии.

Конкретный способ разделения авторизации и нативного состояния выбирается по
результату проверки поддерживаемых механизмов Codex. Подмена общего `auth.json`
под работающими процессами, общие изменяемые credentials для разных аккаунтов,
ручное редактирование внутренних БД/rollout-файлов и симлинки как обход изоляции
не являются принятой схемой. Обновление закреплённого Codex — отдельное решение.

При недоступном штатном механизме продолжения фиксируется blocker; продуктовый
сценарий не заменяется незаметно новым разговором или передачей выжимки.
Наличие этого ADR не означает, что проверка уже пройдена.

## Границы компонентов

- Общий менеджер сохраняет одну регистрацию и установку агента. Учёт подключений
  и выбор аккаунта выделяются из `AgentManager` в отдельные сервисы.
- Адаптер Codex отвечает за авторизацию, общую конфигурацию, нативные причины
  лимита и поддерживаемый способ восстановления. Host не разбирает токены.
- Контроллер перехода отвечает за остановку, журнал и восстановление; worker
  получает привязку к подключению, а не глобально переключаемую переменную среды.
- Схемы хранения/IPC передают безопасные ID и состояния. Кеши статуса, моделей,
  лимитов и ревизии авторизации учитывают подключение и не смешивают аккаунты.
- Renderer собирает существующие компоненты настроек, лимитов и ленты;
  логика выбора аккаунта и восстановления не размещается в UI.

Claude Code и встроенный агент не получают ротацию аккаунтов в рамках этого ADR.
Платные API-ключи, балансировка каждого запроса и изменение модели ради
продолжения также не входят в решение.

## Последствия и альтернативы

Пользователь работает с одним Codex и не управляет маршрутизацией задачи.
Цена решения — отдельные состояния подключений, согласованная обработка
параллельных сессий и аварий, а также обязательная проверка нативного resume.

Отдельные агенты на каждый аккаунт отклонены: дублируют регистрацию и настройки
и заставляют пользователя выбирать исполнителя. Ручной logout/login отклонён:
не обеспечивает независимость параллельных сессий и автоматическое продолжение.
Суммарный процент квоты отклонён: у аккаунтов независимые окна и лимиты.

## Критерии приёмки реализации

- Два реальных аккаунта с одинаковым доступом и сценарий добавления пяти:
  нет искусственного ограничения, дубликатов аккаунта и потери прежнего входа.
- Общие настройки сохраняются, новая задача не требует выбора аккаунта.
- Подтверждённое исчерпание квоты продолжает ту же задачу под другим аккаунтом
  без ручного сообщения, потери нативного контекста и повторных побочных эффектов.
- Несовместимый, неавторизованный или исчерпанный кандидат пропускается;
  исчерпание всех аккаунтов заканчивается понятной остановкой без цикла.
- Сеть, бюджет сессии и временный rate limit не запускают ротацию квоты.
- Параллельные задачи, аварийное восстановление и открытые взаимодействия
  сохраняют единственного писателя и согласованную историю.
- Лимиты отображаются по аккаунтам, событие перехода не дублируется при replay.
- Credentials не попадают в IPC/логи; внешний CLI/IDE не теряет свой вход.
- Выполнены сборка и только затронутые тесты; проверены границы ответственности
  и размеры файлов. UI проверен в штатном scoped Electron на Cat-pilot.

Живые проверки — только с настоящим Codex и аккаунтами владельца на Cat-pilot,
с исключением Chatballs из восстановления, индексации и cleanup, как требует
[контракт проверочного запуска](../builtin-agent-project-scope.md).
Не создавать fake backend, подменные API-ответы или искусственные квоты для
выдачи за живую приёмку. Если настоящее исчерпание лимита недоступно для проверки,
этот критерий остаётся открытым и явно отражается в отчёте.
