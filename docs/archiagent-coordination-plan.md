## Общие правила выполнения

- Не смешивать утверждение документа с разрешением приступить к коду.
- Сохранять единственный путь выполнения через существующие сервисы Skaro.
- Разделять controller/state, policy, операции, контекст, адаптеры и UI.
  Не создавать общий файл, реализующий весь координатор.
- Перед изменением поведения сверять текущий код и фактические миграционные
  данные; приведённые точки входа служат навигацией, не полной спецификацией.
- Новые UI-состояния сначала проходят design gate. Поведение, согласованное
  здесь, не даёт права придумывать экран, layout, тексты или визуальный стиль.
- Для кода выполнять сборку и только затронутые тесты; полный прогон — перед
  релизом или по прямому указанию владельца. Для документации они не нужны.
- Live-проверки выполнять на зарегистрированном Cat-pilot штатным контуром;
  Chatballs исключён также из recovery, индексации и cleanup.
- Без отдельного разрешения не создавать fixtures, mock API, fake backend,
  seed-данные или временные серверы. Недоступный реальный сценарий фиксировать
  как непроверенный с blocker, а не заменять искусственным окружением.
- На каждом этапе сохранять команды, версии входов, исходы и ограничения
  проверки. Отметка приёмки требует наблюдаемого результата, не обещания модели.

## AC-1. Долговечный контроллер проекта

Зависимости: принятый контракт и ADR. С RC-1 согласуются идентичности ресурсов
и владения; модель ресурсов не дублируется в координаторе.

Реализация AC-1 охватывает входящие IPC/MCP/owner-команды. Project version —
счётчик допущенных mutation-намерений, не версия всех файлов. Полные снимки входов
и общая память остаются AC-2; generic IPC с новым ID не дедуплицирует двойной клик.
Полученный failed receipt может иметь частичные эффекты, а неизвестный исход
удерживается до сверки. Подробности и ограничения — в [отчёте](archiagent-coordination-ac1.md).

Работа:

1. Определить типы project coordinator, intent, event, operation, decision и
   blocker; разграничить долговечный статус задачи и runtime-ожидание.
2. Добавить хранилище и миграцию: версия записи, source/scope, причинная связь,
   idempotency key, результат и доказательства фактического эффекта.
3. Реализовать очередь событий с повторной доставкой и единственным владельцем
   мутации проекта. Подтвердить порядок read/validate/commit/dispatch/reconcile.
4. Подключить существующие task/chat/integration handlers как единственный
   исполнитель действий; запретить обход через второй shell workflow.
5. Разделить механические переходы и обращение к модели: модель не нужна
   для доставки, стандартных ожиданий, дедупликации и восстановления записей.

Точки входа: `app-services.ts`, `task-run-engine.ts`, `chat-engine.ts`,
`project-task-mutations.ts`, `owner-commands.ts`, `scoped-port.ts`.

Локальная приёмка AC-1 ([проверки и ограничения](archiagent-coordination-ac1.md#проверки)):

- [x] На проект существует одна логическая идентичность координатора;
  переключение модели или закрытие чата её не меняет.
- [x] Повтор одного event/command ID не повторяет изменение ресурса.
- [x] Два конфликтующих изменения проверяют версию; устаревшее отклоняется
  с сохранённым основанием и не затирает новое состояние.
- [x] Сбой между intent, эффектом и записью результата обнаруживается;
  неизвестный внешний исход сверяется до повторного действия.
- [x] Операции разных проектов не смешивают состояние и полномочия.
- [x] Контроллер обрабатывает допустимые механические переходы без модели.
- [x] Проверены миграция/повторное открытие состояния, целевые проверки,
  сборка и отсутствие NO GOD violations; свидетельства приложены.

## AC-2. Общая память, зависимости и preflight

Зависимости: AC-1, RC-2. Требования к памяти и снимку входов можно уточнять
параллельно RC-2; завершение этапа включает настоящий ресурсный допуск кандидата.

Работа:

1. Направить все новые и восстановленные проектные чаты к координатору,
   сохраняя историю, темы, исходных авторов и действующие scope.
2. Предоставить адресное чтение задач, документов, публичных историй и решений
   внутри проекта. Добавить версионированные краткие представления и
   инвалидировать их при изменении источника; не включать все журналы в prompt.
3. Фиксировать снимок требований, принятых SHA зависимостей, окружения и
   необходимых проверок. Сверять его перед стартом и каждым восстановлением.
4. Разделить зависимости кода, артефактов и готовности сервисов. Preflight
   выявляет цикл и отличает prerequisites от результатов будущей реализации.
5. Подключать точные принятые результаты через существующий integration
   service; сохранять грязный checkout и не применять обновление поверх него.
6. Для разрешённых непубликованных входов использовать неизменный кандидат
   и реальное локальное окружение с проверкой состава и здоровья. Отдельная
   операция может установить проверенную версию в зарегистрированный постоянный
   локальный контур до Git-приёмки, сохранив его данные и возможность восстановления.

Реализация, схема workflow и границы live-приёмки: [отчёт AC-2](archiagent-coordination-ac2.md).

Точки входа: `chat-context.ts`, `chat-context-text.ts`, `history-tool.ts`,
`task-dependency-checkout.ts`, `completion-dependencies.ts`,
`task-run-scheduling.ts`, `integration-service.ts` и
[контракт интеграции](integration-process.md).

Локальная приёмка (объём свидетельств по каждому пункту и непроверенные
реальные сценарии перечислены в [отчёте](archiagent-coordination-ac2.md#проверки-и-свидетельства)):

- [x] Решение из одного чата доступно следующему чату с исходным scope,
  источником и версией; история не превращается в новые права.
- [x] Новый чат не создаёт независимый исполнитель общего состояния проекта.
- [x] Секреты и чужие проекты не доступны через общую память или поиск.
- [x] Изменение требования инвалидирует старое представление и обнаруживается
  при продолжении задачи, в том числе уже имеющей native session.
- [x] Обычный старт не разблокируется одним статусом review зависимости;
  сохраняются ограничения D-45. Для ранее начатых/явно разблокированных задач
  разрешённый результат подключается по точному принятому SHA; изменение
  результата требует перепроверки входов и кандидата.
- [x] Статус done/review сам по себе не объявляет сервис готовым.
- [x] Цикл dependencies и preflight, требующий будущую миграцию заранее,
  выявляются с конкретным объяснением без бессмысленных повторов модели.
- [x] Штатный локальный кандидат запускается без раннего merge в base;
  SHA, состав, проверки и версия окружения зафиксированы.
- [x] Разрешённая установка версии в постоянный локальный контур проверяет
  точную цель, manifest, данные и исключительный lease; не зависит от task
  worktree, не копирует поверх него task-БД и не объявляет Git-приёмку выполненной.
- [x] Незакоммиченная работа сохраняется при обновлении зависимостей и recovery.
- [x] Целевые проверки и сборка пройдены; непроверенные реальные сценарии
  обозначены отдельно, структура модулей проверена.

## AC-3. Блокеры, права и управляемое продолжение

Статус: **завершён в рабочем дереве 12.11.2026, локальная приёмка 11/11**.
Уровни проверок, ограниченный набор исполнителей и evidence — [отчёт AC-3](archiagent-coordination-ac3.md).

Зависимости: AC-2, RC-2. Контракт lifecycle согласуется заранее; RC-3 затем
подключает его к освобождению ресурсов и не является зависимостью этого этапа.
До AC-4 новые решения проходят существующее представление взаимодействий;
глобальное окно ещё не считается реализованным.

Работа:

1. Расширить контракт report blocker: тип, evidence, task/resource IDs,
   попытки, требуемое действие, условие снятия и версия входного снимка.
2. Создавать те же incident из ошибок сервиса/адаптера, когда модель уже
   не работает; объединять только совпадающие причины и версии ресурса.
3. Реализовать этапы диагностики, разрешённого действия, ожидания, проверки
   и разрешения; установить пределы попыток без нового прогресса.
4. Определить три режима координатора: с подтверждением, автоматически по
   правилам, делегированное подтверждение. Хранить ограничения делегирования,
   решение, автора и основание отдельно от sandbox и режима рабочего агента.
5. Применять полномочие к точному действию с проверкой версии, срока,
   отзыва и запретов непосредственно перед dispatch.
6. Сохранять intent каждой задачи и корректно возобновлять подписчиков после
   проверки блокера; обычный вопрос владельца не снимает отдельную паузу.

Точки входа: `task-blocker-tool.ts`, `task-execution.ts`,
`task-run-continuation.ts`, `task-run-events.ts`, `question-answers.ts`,
`task-run-access.ts`, `scoped-port.ts`.

Приёмка:

- [x] Один сбой общего сервиса у нескольких задач создаёт один incident;
  разные причины/версии ресурса не сливаются по похожему тексту.
- [x] Достоверная ошибка запуска/лимита регистрируется без вызова модели.
- [x] Рутинное разрешённое исправление выполняется один раз, проверяется и
  разблокирует только актуальных подписчиков с действующим intent.
- [x] Повторяемый сбой без прогресса останавливает попытки и не расходует
  лимит на переписку агентов или одинаковые вопросы владельцу.
- [x] В каждом режиме подтверждения проверены разрешение, отказ, отзыв,
  истечение срока, изменение входной версии и выход за scope.
- [x] Делегированное подтверждение не повышает права, бюджет и доступ модели;
  явные запреты владельца сохраняются во всех режимах.
- [x] Ответ на вопрос не размораживает явно остановленную работу; ответ на
  конкретное решение продолжает только соответствующую разрешённую операцию.
- [x] Квота, денежный бюджет, переполнение контекста, авторизация и отсутствие
  прогресса имеют отдельные причины ожидания/ошибки и правила восстановления.
- [x] Неизвестный расход не обнуляется; смена модели/аккаунта выполняется
  только в пределах заранее выданной политики.
- [x] Независимые задачи продолжаются; ожидающая не удерживает вычислительный
  слот без необходимости. Совместная приёмка с RC зафиксирована.
- [x] Сборка, затронутые проверки и структурная проверка завершены с evidence.

- [x] Фоновые события отражают подтверждённые исходы с правильной областью;

- [x] В штатном Cat-pilot проверены загрузка, ожидание, ошибка, готовность,

## AC-5. Миграция, восстановление и приёмка координатора

Завершён 13.11.2026: [реализация, приёмка 9/9 и пакет AG-1](archiagent-coordination-ac5.md).

Зависимости: AC-4, RC-3; предыдущие AC-этапы входят в их зависимости.
Это приёмка направления координации. Финальная сквозная приёмка всех
AC/RC/C4 и переключение продукта выполняются отдельно в AG-1
[общего плана](archiagent-plan.md).

Работа:

1. Определить миграцию существующих чатов, активных/ожидающих задач, вопросов,
   legacy blockers и разрешений. Не повышать права и не запускать остановленное.
2. Проверить восстановление на границах intent/эффект/result/answer/delivery,
   отсутствие второго OS-владельца и сверку реального состояния ресурсов.
3. Проверить передачу событий между координатором и ресурсным контроллером;
   housekeeping не зависит от доступности модели. Сохранить контракты для
   совместной приёмки с новым C4 workflow в AG-1.
4. Зафиксировать безопасное отключение новой диспетчеризации: без потери
   истории, повторной доставки действий и возврата отменённых полномочий.
5. Обновить документацию текущего поведения только после фактической
   реализации; отдельно перечислить оставшиеся ограничения и непроверенные случаи.

Приёмка:

- [x] Старые чаты и истории доступны; авторство и решения сохранены;

- [x] Миграция не запускает паузы/отказы и не считает неизвестные legacy
  сведения достаточным доказательством готовности или разрешения.
- [x] После аварийного завершения нет дублирующих работников и эффектов;
  неопределённый исход сначала сверяется с фактическим состоянием.
- [x] В одном реальном сценарии пройдены обнаружение общего блокера,
  единое решение, исправление, проверка и продолжение зависимых задач.
- [x] При недоступной модели сохранены вопросы, intents и история;
  разрешённый housekeeping и механические переходы продолжаются.
- [x] Ожидание квоты не удерживает лишние ресурсы и не снимает запрет
  владельца; повторный допуск опирается на актуальные данные.
- [x] Координатор не создаёт дополнительный обязательный C4 gate;
  контракт передачи значимых архитектурных решений готов к проверке в AG-1.
- [x] Выполнены штатная browser-проверка и затронутые проверки кода, сборка,

- [x] Документированы результаты координации, непроверенные сценарии и
  ограничения; сформирован пакет evidence и оставшихся проверок для AG-1.
