# Skaro v2 — техническая архитектура

Документ описывает целевую архитектуру десктоп-приложения. Решения со статусом «предложено» в [decisions.md](decisions.md) здесь отмечены значком *(предл.)*.

## 1. Общая схема

```
┌──────────────────────── Electron ────────────────────────┐
│  Renderer (Svelte 5 + TS)                                │
│    экраны, вкладки проектов, живой вывод                  │
│            ▲  typed IPC (preload bridge)                 │
│            ▼                                             │
│  Main process (Node + TS)                                │
│    ProjectRegistry   ArtifactStore (+ fs watcher)        │
│    AgentManager ──► ClaudeCodeAdapter / CodexAdapter     │
│    RunQueue          GitService (worktree, merge)        │
│    CheckRunner       SkaroMcpServer                      │
│    AppDb (SQLite)    Notifications                       │
└──────────────────────────────────────────────────────────┘
          │ spawn / SDK                 │ fs, git
          ▼                             ▼
   claude / codex CLI            репозиторий проекта + worktrees
   (авторизация пользователя)    .skaro/  (артефакты)
```

Весь доступ к файловой системе, git и процессам агентов — только в main process. Renderer получает данные и события через типизированный IPC.

## 2. Стек *(предл.)*

- Electron + TypeScript.
- Renderer: Svelte 5 (часть UI-компонентов и стилей v1 переиспользуется).
- Хранилище приложения: SQLite через встроенный `node:sqlite` (есть и в Node, и в Electron; нативных модулей и отдельной сборки под Electron не нужно).
- Git: системный `git` через дочерние процессы (worktree, merge-tree и т.п. проще и надёжнее, чем через JS-библиотеки).
- Сборка и обновления: electron-builder, автообновление через GitHub Releases.

Python-код v1 не используется. Переносятся: промпты (адаптируются под агентов), идеи парсеров, i18n (ru/en), визуальный стиль.

## 3. Артефакты проекта: `.skaro/`

```
.skaro/
  brief.md                  бриф: что строим, для кого, границы
  architecture.md           архитектура + раздел «Правила и ограничения»
  adr/
    0001-<slug>.md          ADR
  specs/
    0001-<slug>.md          спецификация
  milestones/
    M01-<slug>.md           этап
  tasks/
    T-001-<slug>.md         задача
  docs/
    *.md                    свободные документы
  config.yaml               настройки проекта (без секретов)
```

Все файлы — Markdown с YAML frontmatter, человекочитаемые и пригодные для ручной правки. Skaro следит за файлами (fs watcher) и подхватывает ручные изменения.

### 3.1 Этап

```markdown
---
id: M01
title: Базовый API
order: 1
---
## Цель
...
## Критерий готовности
...
```

Статус и прогресс этапа не хранятся — вычисляются по задачам.

### 3.2 Задача

```markdown
---
id: T-012
title: Авторизация по email
milestone: M01
status: todo            # todo | in_progress | review | done | failed | cancelled
depends_on: [T-010]
spec: "0003"            # необязательно: спецификация, которую реализует задача
agent: claude-code      # необязательно, иначе — из config.yaml
model: opus             # необязательно
branch: skaro/T-012-email-auth
order: 3                # порядок внутри этапа
unblocked: true         # только если пользователь разблокировал задачу
archived: true          # только для задач в архиве
created: 2026-09-18
---
## Цель
...
## Критерии приёмки
- ...
## Заметки
...
## Итог
(заполняет Skaro после слияния: краткое резюме агента, ссылки на ADR)
```

- В файле хранится только «долгоживущий» статус. Оперативное состояние (идёт запуск, агент ждёт ответа) живёт в AppDb, чтобы не создавать шум в git.
- «Заблокирована» вычисляется: `status: todo`, задача не разблокирована вручную (`unblocked`) и хотя бы одна задача из `depends_on` не `done`.
- Коммит слияния не может содержать собственный хеш, поэтому история слияний (коммит, стратегия, отмена) хранится в AppDb, а не в файле задачи.
- ID сквозные в пределах проекта, выдаёт Skaro.
- `milestone` необязателен: задача без этапа — точечная доработка или исправление. На плане и доске такие задачи в группе «Без этапа».

### 3.3 План

Отдельного файла плана нет. Экран «План» строится из `milestones/*` (порядок — поле `order`) и `tasks/*` (группировка по `milestone`, связи — `depends_on`). Так план и задачи не могут рассинхронизироваться.

### 3.4 `config.yaml`

```yaml
default_agent: claude-code
default_model: opus
base_branch: main
branch_template: "skaro/{id}-{slug}"
isolation: worktree            # worktree | in-place
checks:
  - name: Тесты
    run: npm test
  - name: Линтер
    run: npm run lint
merge:
  strategy: squash             # squash | merge
  delete_branch: true
chat:
  auto_accept_docs: true       # документы из чата применяются сразу, задачи — всегда с подтверждением
agent_instructions: |
  Дополнительные инструкции, которые получает агент в каждом запуске.
```

### 3.5 Правило владения `.skaro/` *(предл.)*

- `.skaro/` изменяет только Skaro — в основной рабочей копии проекта.
- Агенты меняют артефакты только через MCP-инструменты Skaro (раздел 6).
- В worktree задачи `.skaro/` — снимок только для чтения. Изменения `.skaro/` в ветке задачи при слиянии отбрасываются, пользователь видит об этом предупреждение.

### 3.6 Файлы для агентов вне Skaro

Skaro поддерживает в корне проекта блок в `AGENTS.md` и `CLAUDE.md` (между маркерами, не трогая остальное содержимое) со ссылками на `.skaro/brief.md`, `.skaro/architecture.md`, `.skaro/adr/` и `.skaro/specs/`. Так агент видит контекст проекта, даже если его запустили без Skaro.

### 3.7 Спецификация

Что именно делает функция. Устроена как ADR: свой каталог, сквозной номер, статус.

```markdown
---
id: "0003"
title: Возвраты по картам
status: accepted        # proposed | accepted | superseded
date: 2026-09-26
replaces: "0001"        # необязательно
replaced_by: "0005"     # необязательно
---
## Проблема
...
## Сценарии
...
## Требования
- R-1 ...
- R-2 ...
## Не входит
...
## Открытые вопросы
...
```

- В интерфейсе — `SPEC-0003`. Номер выдаёт Skaro.
- Спецификация живая: описывает, как функция работает сейчас. Задача, которая меняет поведение, предлагает правку спецификации (карточка в ленте). «Заменена» — когда функцию описывает другая спецификация.
- Задачи ссылаются на спецификацию полем `spec`. Критерии приёмки задачи могут ссылаться на требования (`R-2`).
- Для новой функциональности агент чата сначала пишет спецификацию, задачи нарезает после её принятия. Мелкая доработка — задача без спецификации.

## 4. Данные приложения

В каталоге данных приложения (`%APPDATA%/Skaro`, `~/Library/Application Support/Skaro`, `~/.config/Skaro`):

- `skaro.db` (SQLite): список проектов, открытые вкладки, настройки, оперативное состояние задач, индекс запусков и чатов.
- `runs/<project-id>/<task-id>/<run-id>.jsonl` — полный поток событий запуска.
- `chats/<project-id>/<chat-id>.jsonl` — история чатов.
- `attachments/` — вложения пользователя и изображения из вывода агентов, по одному файлу на содержимое (`<sha256>.<ext>`); в логах и ленте — только ссылки.
- `agents/` — докачанные закреплённые версии Claude Code и Codex.
- `imports/<project-id>/<import-id>/` — копия источника импорта документации и артефакты до подтверждения (раздел 12); удаляется после решения.

## 5. Агенты

### 5.1 Интерфейс адаптера

```ts
interface AgentAdapter {
  id: 'claude-code' | 'codex';
  adapterVersion: string;
  status(): Promise<{ installed: boolean; version?: string; authenticated?: boolean; account?: string }>;
  login(): Promise<void>;                       // вход через браузер средствами самого агента
  listModels(cwd: string): Promise<AgentModel[]>;
  listCommands(cwd: string): Promise<AgentCommand[]>; // «/»-команды и навыки
  checkSandbox(scratchDir: string): Promise<SandboxCheck>; // самопроверка песочницы (D-28), без вызова модели
  start(opts: SessionOptions): Promise<AgentSession>;     // cwd, model, effort, permissionMode, planFirst, readOnly, resume, instructions, mcp
}
```

Установка закреплённых версий — отдельный `AgentInstaller` в ядре; адаптер получает путь к установленному бинарнику. Контракт — `packages/timeline/src/agent.ts`.

`AgentSession`, события ленты и модели данных — в [agent-output.md](agent-output.md), раздел 3.

### 5.2 Нормализованные события

Каноническая модель ленты (элементы с жизненным циклом, взаимодействия, план, расход), маппинг Claude Code и Codex на неё и правила устойчивости к изменениям форматов описаны в [agent-output.md](agent-output.md).

UI рендерит только каноническую модель и не зависит от конкретного агента. Сырой поток сохраняется в `.jsonl` и является источником истины: ленту можно пересобрать новой версией адаптера.

### 5.3 Интеграция

- **Claude Code** — через Claude Agent SDK (TypeScript). Разрешения и вопросы — через колбэк `canUseTool`, MCP Skaro — через конфигурацию сессии. Запускается собственный бинарник SDK той же версии, закреплённой релизом Skaro. Он докачивается при первом использовании (см. [agent-output.md](agent-output.md), раздел 6). Task-инструменты плана включаются явно: на новых моделях их нет по умолчанию.
- **Настройки пользователя** (`~/.claude`, `~/.codex`: хуки, MCP-серверы, навыки, глобальные инструкции) подключаются к запускам Skaro (D-25). MCP-сервер Skaro добавляется к ним.
- **Codex** — через `codex app-server` (JSON-RPC v2 по stdio: потоки, события, запросы подтверждений и вопросов). Codex SDK не подходит: он работает поверх `codex exec` без подтверждений и вопросов. MCP Skaro — через конфигурацию запуска. Авторизация во всех случаях — собственная авторизация пользователя в CLI (подписка). Skaro не хранит ключей и токенов.

### 5.4 Режимы прав

| Режим в UI | Смысл |
|---|---|
| Спрашивать | Каждое изменение файла и команда — через подтверждение. |
| Авто в пределах задачи (по умолчанию) | Правки и команды внутри worktree без подтверждения, всё за его пределами — с подтверждением. |
| Полный доступ | Без подтверждений. Требует явного выбора. |

Каждый режим отображается на родные режимы конкретного агента. «Авто в пределах задачи» опирается на песочницу агента; если она границу не держит (так сейчас на Windows у обоих агентов), команды подтверждаются, правки внутри worktree — нет (D-28).

## 6. MCP-сервер Skaro *(предл.)*

Skaro поднимает локальный MCP-сервер и подключает его к каждой сессии агента. Доступ ограничен токеном сессии и областью (проект, задача).

| Инструмент | Где доступен | Подтверждение |
|---|---|---|
| `get_project_context` (бриф, архитектура, ADR, спецификации, этапы) | везде | — |
| `get_task` / `list_tasks` | везде | — |
| `write_doc` (brief, architecture, docs/*) | чат проекта | по настройке `auto_accept_docs` |
| `propose_adr` | везде | в чате проекта — по настройке, в запуске — всегда |
| `propose_spec` (новая спецификация или правка существующей) | везде | в чате проекта — по настройке, в запуске — всегда |
| `stage_artifact` / `finish_import` | чат импорта (раздел 12) | экран проверки импорта |
| `propose_milestones` / `propose_tasks` / `update_task` | чат проекта, чат задачи | всегда |
| `report_progress` | запуск | — |
| `submit_result` (итог работы: вердикт и подтверждение по каждому критерию приёмки) | запуск и чат задачи | — |
| `merge_task` (влить ветку задачи в базовую) | запуск и чат задачи | всегда: карточка подтверждения в ленте |

Предложения агента не применяются сразу. Они появляются в UI как карточки «Принять / Изменить / Отклонить».

**Критерии приёмки.** «Готово» — это не слова агента, а отметки в задаче. Перед тем как сказать, что задача сделана, агент сам проверяет каждый критерий и вызывает `submit_result` с вердиктом и подтверждением (что запускал, что увидел) по каждому. Skaro ставит или снимает галочки в файле задачи по этому отчёту. Если какой-то критерий не выполнен, агент прямо говорит об этом пользователю. Пользователь может поставить или снять галочку вручную — его отметка главная.

## 7. Запуск задачи

1. **Проверка:** задача не заблокирована, есть свободный слот, агент установлен и авторизован.
2. **Изоляция:** `git worktree add` в каталог данных приложения, ветка по шаблону от актуальной `base_branch`.
3. **Промпт:** шаблон задачи = инструкции проекта + ссылки на бриф, архитектуру и спецификацию задачи, если есть `spec` (абсолютные пути в основной рабочей копии: `.skaro/` не обязательно закоммичена и в worktree её может не быть) + текст задачи (цель, пронумерованные критерии приёмки) + итоги задач-зависимостей + правила (работать только в worktree, перед словами «готово» проверить критерии и вызвать `submit_result`).
4. **Выполнение:** сессия агента, события → AppDb/`.jsonl` → renderer. Статус «В работе» ↔ «Нужен ответ».
5. **Завершение:** агент проверяет критерии и сдаёт `submit_result`. Все отмечены — статус «На ревью» и карточка слияния в ленте, системное уведомление. Отмечены не все или агент просто закончил ответ — «Нужен ответ» (задача «В работе», агент не работает), уведомление.
6. **Доработать:** комментарий пользователя уходит в ту же сессию (resume), цикл повторяется.
7. **Отклонить:** worktree и ветка удаляются, задача → «Не начата» (запуск остаётся в истории).

### 7.1 Параллельность

- `RunQueue` с настраиваемым числом слотов (по умолчанию 3).
- Запускать можно только незаблокированные задачи. Если слотов нет, задача ставится в очередь.
- Задачи без зависимостей друг от друга могут изменять одни и те же файлы. Конфликты выявляются при слиянии (раздел 8), а не запрещаются заранее.

## 8. Слияние

Слияние выполняет Skaro, **только по явному подтверждению пользователя**.

**Как запускается (D-27).** Отдельного экрана ревью и кнопок слияния вне ленты нет. Когда все критерии приёмки отмечены (`submit_result` или галочки пользователя), Skaro сам показывает в ленте задачи карточку подтверждения — или, если в общих настройках Skaro включено «Вливать автоматически» (настройка приложения `merge.auto`), сразу коммитит и вливает ветку, а агент сообщает о слиянии в ответе; заблокированное слияние и тогда показывает карточку; снятая галочка убирает её и возвращает задачу в работу. Кроме того, пользователь может написать в чате задачи («вливай»): агент вызывает инструмент MCP Skaro `merge_task`, и Skaro показывает в ленте карточку подтверждения: что вливается, куда, сколько файлов, результаты проверок ниже. Пользователь подтверждает, Skaro выполняет слияние. Сам агент в основную ветку не пишет: он работает только в worktree, а безопасность слияния и обработку `.skaro/` берёт на себя Skaro. `merge_task` не ждёт решения пользователя: Skaro коммитит в ветку задачи всё, что агент не закоммитил, проверяет слияние, показывает карточку и сразу отвечает агенту. После слияния сессия агента закрывается и worktree удаляется, когда агент закончит текущий ответ.

**Проверки перед слиянием** (показываются в диалоге подтверждения). До карточки: пока в задаче есть неотмеченные критерии приёмки, `merge_task` карточку не показывает и отвечает агенту, какие пункты не отмечены. Блокируют слияние:

1. Основная рабочая копия не чистая (незакоммиченные изменения отслеживаемых файлов) или в ней выбрана не базовая ветка. Незакоммиченные изменения `.skaro/` не блокируют: так Skaro держит статусы задач до слияния; при слиянии они сохраняются, а файл задачи коммитится вместе с кодом.
2. В ветке задачи нет изменений кода.
3. Пробное слияние (`git merge-tree`) даёт конфликты. Если есть конфликты — кнопка «Разрешить конфликты с агентом»: агент получает от `merge_task` описание конфликта, выполняет rebase в worktree и снова вызывает `merge_task`.
Не блокируют, а предупреждают:

- базовая ветка ушла вперёд — предлагается «Обновить ветку задачи» (rebase в worktree);
- ветка меняет `.skaro/` — эти изменения будут отброшены.

**Слияние:**

- Стратегия из `config.yaml` (по умолчанию squash, сообщение коммита генерируется из задачи и резюме агента, редактируется в диалоге).
- Вместе с кодом коммитится обновлённый файл задачи (`status: done`, «Итог»).
- Worktree удаляется, ветка удаляется по настройке.
- Зависящие задачи разблокируются, пользователь получает уведомление.
- **Отменить слияние** — `git revert` коммита слияния, задача возвращается в «На ревью». Кнопка доступна в истории задачи.

Push в удалённый репозиторий Skaro не делает.

## 9. Чаты

- **Чат проекта** — агент работает в основной рабочей копии в режиме «Спрашивать» (правки и команды — после подтверждения в карточке) или «Полный доступ» — выбор в модалке «Агент чата» и имеет MCP-инструменты для документов, ADR, этапов и задач. Несколько чатов на проект.
- **Чат задачи** — агент только читает код и контекст задачи, может предлагать изменения описания задачи и новые задачи (например, разбить задачу на две). Код не меняет.
- **Чат импорта документации** — особый чат проекта (раздел 12).
- **Стартовый экран чата** зависит от проекта. Нет кода: «Опишу идею», «Импортировать документацию». Есть код: «Новая фича» (спецификация → задачи), «Доработать или исправить» (сразу задача), «Импортировать документацию». Бриф и архитектура для существующего проекта необязательны, Skaro их не требует.

## 10. Безопасность

- Renderer без доступа к Node (`contextIsolation`, `sandbox`), только IPC-мост с белым списком методов.
- MCP-сервер слушает только localhost, у каждой сессии свой токен.
- Команды проверок берутся только из `config.yaml` проекта и показываются пользователю при первом запуске в проекте.
- Никакие данные не отправляются наружу, кроме того, что отправляют сами агенты. Телеметрия — только по явному согласию.

## 11. Перенос из v1

- Код v1 — в ветку `legacy/v1` и тег `v1-final`. В `main` новая кодовая база.
- Импорт `.skaro/` v1 (constitution → раздел архитектуры, devplan → этапы, milestones/tasks → задачи) — после MVP.

## 12. Импорт документации

Документация пользователя переносится в формат Skaro агентом, один раз, с подтверждением. Skaro не читает чужие форматы документации как свои: после импорта источник истины — `.skaro/`.

### 12.1 Источник

- Папка, файлы или архив (zip) — где угодно на диске, не обязательно в репозитории. Можно несколько источников сразу.
- Ссылки на веб-страницы не поддерживаются: страницу выгружают в файл (Confluence, Notion — экспорт в zip или html).
- Код проекта всегда второй источник: агент сверяет описанное с тем, что есть на самом деле. Если документации нет, импорт «из кода» работает так же.

### 12.2 Копия источника

Skaro копирует источник в `imports/<project-id>/<import-id>/` в данных приложения и переводит в текст всё, что может. Агент работает только с копией: ему не нужен доступ к исходной папке, и оба агента видят одно и то же.

| Формат | Что делает Skaro |
|---|---|
| md, txt, rst, adoc, yaml, json | копирует как есть |
| docx | Markdown (mammoth) |
| html, выгрузки Confluence и Notion | Markdown (turndown) |
| pdf | текст (pdfjs), оригинал рядом |
| xlsx, csv | таблицы Markdown |
| png, jpg, svg | копирует, агент смотрит сам |
| zip | распаковывает, содержимое — по этой же таблице |
| прочее | в «Не перенесено» с причиной «формат не поддерживается» |

Рядом — `manifest.json`: исходный путь, путь копии, формат, размер, что сделано с файлом. Источник не меняется. Копия удаляется после применения или отклонения импорта.

### 12.3 Чат импорта

- Чат проекта с заголовком «Импорт документации», режим прав как у любого чата проекта. Копия источника подключается к сессии как дополнительный каталог для чтения.
- Промпт: `manifest.json`, шаблоны всех типов Skaro (бриф, архитектура с «Правилами и ограничениями», ADR, спецификация, этап, задача), текущие артефакты проекта и правила:
  - переносить смысл, а не копировать текст; один источник может дать несколько артефактов и наоборот;
  - сверять с кодом; противоречия источников между собой и с кодом — вопросом пользователю, если без ответа нельзя, иначе — пометкой в итоге;
  - решения с обоснованием — в ADR; описания функций — в спецификации; правила для агентов — в раздел «Правила и ограничения»;
  - открытые пункты бэклога и роадмапа — в этапы и задачи; сделанное задачами не становится;
  - всё, что не легло ни в один тип, — свободным документом в `docs/`; ничего не выбрасывать молча;
  - если у проекта уже есть артефакт того же смысла — предлагать правку, а не новый.
- Ход работы — обычная лента чата. Пользователь может вмешаться сообщением («ADR не переноси»).

### 12.4 Инструменты

- `stage_artifact(type, key, title, body, sources[], updates?, …)` — кладёт готовый артефакт в промежуточную папку импорта, не в `.skaro/`. `type`: brief, architecture, adr, spec, doc, milestone, task. `key` — временный ключ артефакта; в тексте на другой артефакт импорта ссылаются как `{{key}}`, у задачи — полями milestone, depends_on, spec. `sources` — пути из манифеста или `code`. `updates` — номер ADR или спецификации, имя документа, который правится (бриф и архитектура правятся, если уже есть). Номера выдаёт Skaro при применении.
- `finish_import(skipped[], notes)` — закрывает импорт: что не перенесено и почему, допущения и расхождения. Skaro добавляет к `skipped` файлы, которые не смог прочитать сам.

Skaro проверяет каждый артефакт (frontmatter, обязательные разделы, ссылки). После `finish_import` в ленте появляется карточка «Импорт готов».

### 12.5 Подтверждение и применение

- Экран проверки: артефакты по разделам, у каждого галочка, «новый» или «обновит», источники, просмотр (для правки — дифф). Этапы с задачами внутри; снятый этап снимает свои задачи. Отдельно — «Не перенесено» и «Допущения и расхождения».
- «Импортировать выбранное»: Skaro выдаёт номера (ADR, спецификации, этапы, задачи), подставляет их в ссылки и записывает выбранное в `.skaro/` одним действием. Если выбранный артефакт ссылается на снятый, ссылка убирается; на экране это видно заранее.
- Решение уходит агенту заметкой `<skaro-note>`, как решения по карточкам. Карточка сворачивается в итоговую строку, артефакты появляются в «Изменено в чате».
- Отклонить импорт — удалить промежуточную папку и копию; `.skaro/` не меняется.
