# Сдача результата не блокирует создание диагностического чата

Исправление от 16.11.2026 относится к двум связанным отказам: незавершённая
`submit_result` удерживала проектную мутацию, а `chat.create` попадала в ту же
очередь. Исключение Git могло содержать десятки мегабайт diff и раздуваться
при сериализации ответа, не оставляя доступного пути сверки исходного вызова.

## Границы исполнения

- Создание чата регистрирует беседу и сообщение в существующем inbox через
  отдельный control scope. Оно не изменяет исходники, критерии или приёмку
  и не повышает версию проектных мутаций. Инструменты агента сохраняют прежние
  права и блокировки. Повтор command ID возвращает ту же беседу.
- Старую `queued` регистрацию чата можно перенести в control scope только
  до claim. ID, fingerprint аргументов, event и intent сохраняются. Уже
  начатые и неизвестные операции так переносить нельзя.
  Перезапуск сохраняет эту регистрацию для явного повтора владельцем;
  сам контроллер не восстанавливает её аргументы и не запускает её автоматически.
- Отпечаток C4 читает Git diff потоком. JSON-формат хеша совместим с прежними
  проверками, включая экранирование и многобайтный текст. Содержимое
  незакоммиченных файлов также хешируется потоком.
- Ошибка Git содержит ограниченную диагностику и исходную причину.
  Ответ сдачи дополнительно ограничен 64 КиБ; большой ответ сохраняет
  свой исход, размер и digest без пересылки всего содержимого.

## Достоверный исход и восстановление

`submit_result` сохраняет terminal receipt, связанный с operation ID,
fingerprint, проектом, задачей и run. Известное исключение обработчика
становится `failed` с возможными частичными эффектами. Это не rollback
и не разрешение повторить исходный вызов. Если потерялось только подтверждение,
контроллер сверяет receipt без нового исполнения.

Принятый результат сохраняет ту же идентичность сдачи вместе с точным SHA
до проекции статуса. Это позволяет отличить принятие с незаконченной проекцией
от результата другой сдачи. Одних галочек критериев недостаточно. Запись
receipt неизменна; Stop, код, C4, критерии и разрешения восстановление не сбрасывает.

`reconcile_task_submission(operation_id)` доступен в задаче и чате её проекта.
Он читает receipt или точный принятый результат. Для старой Codex-операции
допускается сохранённый ответ с явным `isError` либо native `failed` с полученным
ответом и без transport error: должны совпасть аргументы,
scope и единственная исполненная операция во временном окне native-вызова.
Неоднозначность, обычный текст агента и отсутствие записи о результате
не снимают блокировку. Чтение журнала выполняется в background worker;
полная история и большой ответ не передаются в main/renderer.

После подтверждения старого исхода ожидавшие его неисполненные сдачи той же
задачи отклоняются с требованием свежей сверки. Исходная сдача не повторяется.
Повторная сверка уже завершённой операции не отменяет новые запросы.

Проверки используют настоящий Git и SQLite и чистые metadata DTO, без fake
backend, API, runtime или новых проектных fixtures. Живой запуск приложения
не выполняется по указанию владельца оставить рабочий Skaro открытым.
Чтение сохранённого журнала T-188 является диагностикой прежнего исхода,
не новым выполнением или приёмкой Chatballs.
