# Журнал решений Skaro v2

Короткий реестр принятых решений по переходу на v2. Подробности — в [product.md](product.md), [architecture.md](architecture.md), [agent-output.md](agent-output.md).

Статусы: **принято** — согласовано с владельцем продукта; **предложено** — рабочая гипотеза, можно пересмотреть; **пересмотрено** — заменено более поздним решением, указано каким.

| # | Решение | Статус |
|---|---|---|
| D-01 | Skaro — десктоп-приложение на Electron (Windows, macOS, Linux). CLI и web-дашборд v1 не развиваются. | принято |
| D-02 | Skaro не пишет код сам и не содержит BYOK-адаптеров к LLM. Вся работа с моделями — через установленные у пользователя coding-агенты: Claude Code и Codex. | принято |
| D-03 | Агенты работают по подписке пользователя (его собственная авторизация в CLI). API-ключи не требуются. | принято |
| D-04 | Skaro — оркестратор и инструмент контроля: проекты, документация, этапы, задачи, запуск агентов, живой вывод и слияние. | принято |
| D-05 | Поддержка агентов — через единый интерфейс адаптера. Claude Code и Codex — в первой версии, остальные агенты добавляются адаптерами. | принято |
| D-06 | Целевой пользователь v2 — разработчик-одиночка. Skaro Cloud (команды, бюджеты, доступы) — позже, как платная часть. | принято |
| D-07 | Разработка продолжается в существующем репозитории `skarodev/skaro` (сохраняем звёзды). Код v1 сохраняется в ветке `legacy/v1` и теге `v1-final`. | принято |
| D-08 | Артефакты проекта: бриф, архитектура (включая правила и ограничения), ADR, спецификации (D-30), этапы, задачи, свободные документы. Конституции нет — её роль берёт раздел «Правила и ограничения» архитектуры. | принято |
| D-09 | Фич как отдельной сущности нет. Новая функциональность обсуждается с агентом в чате и превращается в задачи. Заменено D-30: без описания функции требования размазываются по критериям задач и теряются после слияния. | пересмотрено |
| D-10 | Отдельного документа плана нет. План — вычисляемое представление: этапы + задачи + зависимости. | принято |
| D-11 | Фазы v1 (constitution → architecture → clarify → plan → implement → tests) упраздняются. Вместо них — жизненный цикл задачи: не начата → в работе → на ревью → готово. | принято |
| D-12 | Каждый запуск задачи по умолчанию идёт в отдельном git worktree и ветке. Это обязательно для параллельного выполнения. | принято |
| D-13 | Слияние выполняет Skaro, только после явного подтверждения пользователя и с проверками безопасности (см. architecture.md, раздел «Слияние»). | принято |
| D-14 | Чат с агентом есть на уровне проекта (планирование, документация, новые задачи) и на уровне задачи. Уточнение текущей реализации: чат проекта поддерживает «Спрашивать» и «Полный доступ»; разговор в запущенной задаче относится к её рабочей сессии и выбранному режиму прав. Права не отменяют ограничения владельца. См. architecture.md, раздел 9. | принято |
| D-15 | Автопилот (автоматический запуск всех готовых задач по графу) — не в первой версии. | принято |
| D-16 | Skaro поднимает собственный MCP-сервер, через который агенты читают и изменяют артефакты проекта (задачи, документы, ADR). Изменения задач агентом требуют подтверждения пользователя. | предложено |
| D-17 | Каталог `.skaro/` в репозитории меняет только Skaro (в основной рабочей копии). Изменения `.skaro/` внутри веток задач при слиянии отбрасываются. | предложено |
| D-18 | Логи запусков агентов хранятся в данных приложения, а не в репозитории. В файл задачи попадает только итог. | предложено |
| D-19 | Стек: TypeScript целиком (Electron main + Svelte 5 renderer). Без Python-сайдкара. UI-компоненты и промпты v1 переиспользуются выборочно. | предложено |
| D-20 | Вывод агентов проходит три слоя: транспорт → адаптер агента → каноническая модель ленты. Интерфейс не знает нативных форматов агентов (см. agent-output.md). | предложено |
| D-21 | Сырой поток агента — источник истины. Каноническая лента — пересобираемая проекция с версией адаптера. | предложено |
| D-22 | Изменённые файлы, diff и статус проверок Skaro вычисляет сам (git, CheckRunner), а не берёт из вывода агента. | предложено |
| D-23 | Claude Code подключается через Agent SDK с его собственным бинарником, Codex — через `codex app-server` (JSON-RPC v2). Версии обоих агентов закреплены релизом Skaro, бинарники докачиваются при первом использовании. | принято |
| D-24 | В ленте агента поддерживаются: откат к сообщению, повтор ответа, редактирование отправленного, режим «сначала план» с одобрением, смена режима прав на лету, вход в агента из Skaro. Смена агента в начатом чате запрещена (см. agent-output.md, раздел 7). | принято |
| D-25 | Пользовательские настройки агентов (`~/.claude`, `~/.codex`: хуки, MCP-серверы, навыки, глобальные инструкции) подключаются к запускам Skaro. | принято |
| D-26 | Закреплённые версии агентов обновляются раз в 2–4 недели и внепланово при выходе новой модели. Перед обновлением — ночная канарейка и golden-тесты адаптеров (см. agent-output.md, раздел 8). | предложено |
| D-27 | Отдельного ревью нет. Слияние подтверждается карточкой в ленте задачи, слияние выполняет Skaro (D-13). Карточка появляется сама, когда отмечены все критерии приёмки (отчёт агента `submit_result` или галочки пользователя), — задача переходит в «На ревью». Пока критерии не отмечены, Skaro не вливает; по просьбе пользователя агент может запросить карточку через `merge_task`. В общих настройках Skaro («Настройки» → «Выполнение») можно включить автоматическое слияние: когда критерии отмечены, Skaro сам коммитит и вливает задачу, агент сообщает об этом в ответе; если слияние заблокировано (конфликты или локальные правки, которые будут перезаписаны), показывается карточка. | принято |
| D-28 | Режим «Авто в пределах задачи» обещает границу, только если песочница агента её держит. Перед первым запуском Skaro проверяет песочницу (агент пробует записать файл за пределами рабочей папки). Не удержала — правки внутри worktree идут без подтверждения, команды подтверждаются, в модалке агента пометка «песочница недоступна — команды подтверждаются». Claude на Windows — `acceptEdits` (песочницы Bash на Windows нет); Codex — песочница `elevated`, если прошла проверку, иначе `untrusted`. Страховка во всех случаях — worktree и git (см. agent-output.md, раздел 9.1). | принято |
| D-29 | Codex подключается с `experimentalApi`: без него недоступны вопросы агента (`requestUserInput`), режим «сначала план» (`collaborationMode: plan`) и субагенты. Проверено прототипом (agent-output.md, раздел 9). Экспериментальную часть протокола отдельно отслеживает канарейка (D-26). Уточняет D-23. | принято |
| D-30 | Спецификация — отдельный тип артефакта, устроенный как ADR: `.skaro/specs/0001-<slug>.md`, сквозной номер (`SPEC-0001`), статусы «предложена / принята / заменена». Описывает, что делает функция: проблема, сценарии, требования `R-n`, что не входит, открытые вопросы. Живой документ: задача, меняющая поведение, предлагает его правку. Задача ссылается на спецификацию полем `spec`, агент задачи получает её в промпте. Новая функциональность — спецификация, затем задачи; мелкая доработка — задача напрямую. Обязательной фазой спецификация не становится (см. architecture.md, 3.7). | принято |
| D-31 | Чужая документация не используется как есть. Её однократно переносит в формат Skaro агент — импорт документации: источник — папка, файлы или архив где угодно на диске, в любом формате; Skaro снимает копию и переводит её в текст, источник не меняет; агент раскладывает содержимое по типам Skaro (включая этапы и задачи из бэклога), сверяясь с кодом; пользователь подтверждает результат на одном экране проверки с галочками. Ссылки на веб-страницы не поддерживаются (см. architecture.md, 12). | принято |
| D-32 | Существующий проект не обязан иметь бриф и архитектуру. Стартовый экран чата предлагает по ситуации: без кода — «Опишу идею», «Импортировать документацию»; с кодом — «Новая фича», «Доработать или исправить», «Импортировать документацию». Задача может быть без этапа — группа «Без этапа» на плане и доске. | принято |
| D-33 | Слияние завершает сессию, сохраняя worktree и ветку. Повторный запуск переиспользует checkout. Удаление блокируется при наличии изменённых/неотслеживаемых/игнорируемых файлов, Docker bind mounts или невозможности проверить mounts. Данные окружения хранятся вне worktree; новые сессии задач получают изолированный официальный Playwright MCP. См. task-environments.md. | принято |
| D-34 | Несвязанные локальные правки не блокируют слияние. Коммит готовится в служебном worktree, применяется с сохранением пользовательских файлов и staging. Слияния одного репозитория выполняются последовательно; открытые карточки обновляются без хода агента. Общий знак ошибки у группы действий убран, неудачная команда выделяется существующим цветом ошибки. Прямое указание владельца от 30.09.2026; см. task-merging.md. | принято |
| D-35 | По указанию владельца от 01.10.2026 актуальный дизайн уже находится в коде: renderer desktop и общие UI-компоненты/токены. Старые HTML-макеты удалены; задания дизайнеру сохраняются только как история. Не восстанавливать прежний UI. Новые элементы, состояния и отклонения требуют прямого решения владельца. Источник и правила — [ui-baseline.md](ui-baseline.md). Статус реализации и оставшаяся работа — в актуализированном плане. | принято |
