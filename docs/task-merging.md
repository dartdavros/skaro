# Слияние параллельных задач и локальные правки

Незакоммиченные изменения основной копии сами по себе не блокируют слияние.
Skaro блокирует его, если результат слияния затронет локально изменённые пути.
Учитываются обе стороны staging, удаления и переименования, новые и игнорируемые
файлы, а также замена файла каталогом и обратно. В карточке перечисляются
конкретные локальные пути. Конфликты между ветками показываются отдельно.

Новый локальный файл не блокирует слияние, если ветка добавляет обычный файл
по тому же пути с побайтно одинаковым содержимым и совместимым executable mode.
Он принимается через служебный index без перезаписи рабочей копии. Различия
содержимого, staged-правки, симлинки и пересечения файла с каталогом по-прежнему
блокируют слияние. Проверка повторяется при публикации.

## Подготовка и применение

### Выход из `dirty_base` (23.10.2026)

По поручению владельца блокировка локальными правками имеет продолжение через
существующее действие «Разрешить конфликты с агентом». В автоматическом режиме
и при явном `merge_task` Skaro начинает этот процесс без повторного подтверждения.
В ручном режиме действие карточки разрешает весь процесс, включая последующее
слияние; повторно нажимать «Влить» после работы агента не требуется.

Перед запуском сохраняются исходные файлы, Git index и отдельные снимки staged
и working tree в `.git/skaro-local-changes/` и `refs/skaro/local-changes/`.
Основная рабочая копия не очищается, stash не используется. В сохраняемом
изолированном кандидате сначала объединяется результат задачи с базой, затем
локальные staged-правки, затем unstaged/untracked-правки затронутых путей.
Конфликты разрешает штатный агент интеграции; проверки выполняются штатными
сервисами на конечном кандидате. В чате используются существующие лента,
вопросы агента и управление остановкой/продолжением интеграции.

В коммит задачи попадает только результат задачи. Совмещённые локальные слои
применяются отдельно в index и рабочие файлы: staged остаются staged, unstaged
остаются unstaged. Несвязанные локальные изменения сохраняются. Исходный
снимок остаётся доступен после завершения; он не удаляется вместе с кандидатом.

Перед публикацией повторно сверяются база, затронутые записи index и образы
локальных файлов. Изменившиеся входы вызывают новую подготовку и автоматическое
продолжение с прежним разрешением на слияние. Операция и её границы слоёв
сохраняются до запуска агента и продолжаются после перезапуска приложения.
Финальная публикация использует общий журнал восстановления и index lock;
ошибка публикации восстанавливает исходные локальные слои. Ошибки окружения,
вопросы агента и явная остановка сохраняют кандидат и используют существующий
сценарий продолжения в чате, без требования вручную выполнять Git-команды.

- Код объединяется и проверяется в сохраняемом служебном worktree с detached HEAD
  и штатным окружением интеграции. Короткий checkout окончательной публикации
  добавляет метаданные задач. Локальные пользовательские правки основной копии
  не включаются в коммит задачи. См. [integration-process.md](integration-process.md).
- Изменения `.skaro/` из ветки задачи отбрасываются. В коммит добавляется только
  подготовленный Skaro файл текущей задачи. Исходный файл проверяется на
  конкурентные правки, остальные файлы `.skaro/` сохраняют содержимое и staging.
- Подготовленный результат применяется через отдельный Git index с блокировкой
  основного index. Git переносит несвязанные staged/unstaged изменения без
  автоматического stash или коммита пользовательской работы.
- Базовая ветка обновляется с проверкой ожидаемого предыдущего коммита.
  Проверки повторяются перед применением: предварительная карточка не является
  разрешением перезаписать изменения, появившиеся позднее.
- При ошибке восстанавливаются только файлы, изменённые этой операцией.
  Общего `reset --hard` в слиянии нет. Конкурентные правки не перезаписываются.

Публикация Git ref и файловой системы не является одной атомарной операцией.
На время применения Skaro сохраняет исходный index и образы изменяемых файлов
в `.git/skaro-merge-recovery-*`. После успешного применения или полного отката
они удаляются. При неполном восстановлении сохраняются исходные данные и путь
к ним, дальнейшее слияние останавливается. Восстановление после аварийного
завершения проверяет владельца, индекс, файлы и SHA по журналу; при несовпадении
данные сохраняются и публикация блокируется. Удалять эти данные для обхода нельзя.

## Параллельность и карточки

`submit_result` подчиняется настройке автоматического вливания: в ручном режиме появляется карточка. Явная просьба пользователя через `merge_task` выполняет ту же операцию слияния без повторного подтверждения. Общий чат указывает task_id или milestone_id. Проверки и реальные препятствия применяются одинаково ко всем путям.

Повторный `merge_task` для завершённой задачи возвращает её статус и коммит из
журнала слияний, если он есть. Git-операции и новая карточка не запускаются.
Завершение без записанного слияния не выдаётся за успешное слияние. Уже устаревшая
карточка закрывается при открытии чата завершённой задачи и при её перепроверке.
После сообщения об успешном слиянии агенту запрещён повторный вызов ради подтверждения.
Запросы инструмента, создание карточек и подтверждения проходят одну очередь проекта.

Агенты работают параллельно в своих worktree. Слияния в один репозиторий
выполняются последовательно, каждое проверяется относительно актуальной базы.
Очередь основной Git-операции общая для экземпляров GitService этого процесса;
конкурирующие внешние Git-процессы дополнительно защищены index lock и проверкой
предыдущего коммита. Работа внешнего редактора не блокируется глобально.

Открытые карточки перепроверяются каждые 1,5 секунды и после завершения слияния.
Повторный ход агента не требуется. Сохраняются идентификатор карточки и введённое
сообщение коммита; событие отправляется только при изменении результата проверки.

## Проверки перед слиянием и его отмена

Решение владельца от 01.10.2026: команды `checks` из `.skaro/config.yaml`
запускаются последовательно перед применением слияния. Формат:

```yaml
checks:
  - name: Tests
    run: node --test
```

Команды выполняются в сохраняемом кандидате с объединённым кодом и его штатным
окружением. Ошибка команды, изменение tracked-файлов или staging,
некорректный config блокируют применение. Главная ветка и статус задачи сохраняются.
Зависимости и окружение команд должны быть доступны: Skaro не копирует автоматически
`node_modules` и не подменяет отсутствующие сервисы. Сохранение параметров проекта
сохраняет список checks и отказывается перезаписывать ошибочный config.

В итоговой строке «Влито в …» есть «Отменить слияние» со штатным подтверждением.
Отмена создаёт Git-коммит и возвращает задачу в review, сохраняя worktree/ветку.
Для rebase отменяется весь записанный диапазон, для merge используется первый parent.
История до добавления записи исходного HEAD не позволяет безопасно определить диапазон
старого rebase; такое слияние требует ручного разбора. Конфликты и локальные tracked-правки
блокируют отмену без перезаписи пользовательской работы. Итоговая строка и журнал
сохраняют отмену после перезапуска.

Проверено 02.10.2026: 26 узких Git/undo тестов, 5 CheckRunner тестов и сборка.
В настоящем Electron оба агента выполнили задачу, слияние, перезапуск, отказ от

## Слияние этапа

С 12.10.2026 (D-45) этап не сливается: каждая задача вливается сама, см.
[completion-process.md](completion-process.md). Абзац ниже описывает прежний порядок.

Этап не создаёт агента или отдельную ленту. Один сервис объединяет сохранённые результаты задач, проверяет их и публикует статусы done в той же операции. Карточка находится в чате реальной задачи. Ход слияния (лента агента, его вопросы, «Стоп», сообщения) с 12.10.2026 показывается и управляется из чата любой задачи этапа, а не только первой: см. [integration-process.md](integration-process.md). Стратегия проекта применяется к общей операции; сообщения задач сохраняются в её описании. Старые рабочие каталоги и история сохраняются. Полный контракт и миграция: [completion-process.md](completion-process.md).

## Индикация ошибок в ленте

По прямому указанию владельца от 30.09.2026 общий крестик ошибки у группы
действий убран. Он ошибочно представлял историческую неудачную попытку как
ошибку всей группы даже после успешного повторного выполнения.

Неудачная команда в раскрытой группе сохраняет свою историю и выделяется
существующим цветом `--sk-error`. Код завершения и вывод относятся только к
ней. Успешная повторная команда сохраняет обычный стиль. Новый знак ошибки,
иконка, layout или состояние группы не добавляются.

Список локальных препятствий использует существующий список файлов карточки
слияния; изменён текст прежней блокирующей строки. Эти изменения поведения и
индикации согласованы владельцем в запросе. Остальные элементы сохраняются по
текущему [UI baseline](ui-baseline.md), а не по удалённым HTML-макетам.
