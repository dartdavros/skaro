# Подтверждение полного плана в чате проекта

По принятому 11.11.2026 [ADR-0049](adr/0049-project-archiagent.md) целевой
архиагент проверяет выполнимость порядка до запуска и согласует связанные
изменения требований, архитектуры и задач одним решением по политике прав.
Новый [порядок C4](c4-workflow.md) и [план перехода](archiagent-plan.md)
ещё не реализованы. Границы задач и сохранность принятых требований остаются.

Агент готовит полный план, владелец подтверждает его один раз, Skaro создаёт
все выбранные задачи и зависимости между ними. Порядок этапов и номера T-xxx
не требуют действий владельца.

## Границы задач

По поручению владельца от 08.10.2026 небольшая связанная работа по умолчанию
оформляется одной задачей. План содержит минимальное число задач с законченными,
проверяемыми результатами. Реализация результата, необходимые тесты, документация
и проверка входят в ту же задачу. Разные файлы, технические слои, требования,
критерии приёмки и шаги чеклиста сами по себе не требуют отдельных запусков.

Разделение оправдано самостоятельными полезными результатами, конкретной пользой
параллельного выполнения либо объёмом, который не помещается в одну ограниченную
по масштабу агентскую сессию. Тесно связанные последовательные шаги остаются
вместе; несвязанные результаты не объединяются в одну огромную задачу.
Критериев должно быть столько, сколько нужно для проверки результата:
ограничения «2–6» и целевого количества задач нет.

Перед предложением или сохранением плана агент объединяет части одного результата
и указывает причину каждого оставшегося разделения в заметках задач. Он учитывает,
что отдельная задача требует своей сессии, ветки и worktree, а также может
потребовать установки зависимостей, запуска окружения и проверок интеграции.
Этап группирует задачи, но не делает их checkout и окружение общими (D-40).
Одиночная локальная задача не требует этапа или многошагового планирования.

Например, небольшое изменение поля формы, его обработки в API и необходимых
тестов — одна задача с несколькими критериями. Разделять её на «поле»,
«обработчик», «тесты» и «документацию» без самостоятельных результатов не следует.

Единые инструкции находятся в
`packages/mcp-server/src/task-decomposition.ts`. Они включены в новый чат,
каждое сообщение продолжаемого чата, импорт документации и описания инструментов
`propose_milestones`, `propose_tasks`, `prepare_plan`, `stage_artifact`.
Это правила для агента: структурная валидация плана не оценивает смысл границ
и не гарантирует качество ответа модели. Уже созданные или принятые задачи
автоматически не объединяются; агент предлагает единый пакет через
[`replan_tasks`](task-replanning.md), владелец подтверждает его один раз.
Менять можно только фактически не начатые задачи. Явные указания владельца
о границах задач имеют приоритет.

## Сохранение и подтверждение

`prepare_plan` сохраняет полные записи задач, целевые этапы, ссылки на
спецификации, зависимости и покрытие требований. Количество должно совпадать
с `expected_total`; неизвестные зависимости, циклы и непокрытые требования
не принимаются. Семантическое качество декомпозиции по-прежнему требует
сверки со спецификацией: одних счётчиков недостаточно.

`propose_saved_plan` показывает ОДНО предложение всего сохранённого плана.
Устаревший аргумент `milestone` не разбивает его на отдельные подтверждения.
Все связанные спецификации должны быть приняты перед показом полного плана.
Если часть спецификаций ещё не готова, декомпозиция сохраняется целиком,
а отдельные готовые этапы не выдаются за законченный план.

`finish_plan` проверяет полноту предложения; его успех не означает, что
владелец подтвердил план или что задачи уже созданы. Контекст возвращает
фактические состояния: подготовлено, предложено, ожидает решения, создаётся,
создано, отклонено, отсутствует. Созданные задачи сверяются с файлами проекта.
Повторные вызовы не дублируют предложение и не возвращают отклонённый план.

В единой карточке перечислены все задачи и их этапы, используется текущий
визуальный baseline. Один набор действий: «Отклонить» и «Подтвердить план».
Выбор задачи включает необходимые зависимости; снятие зависимости снимает
зависящие от неё задачи. Это поясняется подсказкой флажка. Уже созданные задачи
при восстановлении показаны с номерами и не создаются повторно.

Перед сохранением подтверждения backend проверяет весь выбранный граф,
спецификации и существование этапов. Некорректный набор не создаётся частично.
После подтверждения задачи записываются в порядке зависимостей, со всеми
связями сразу. Нет состояния «ждёт принятия другой карточки», переходов к
предшественникам и кнопки «Повторить». При настоящем сбое записи показывается
конкретная ошибка; решение сохраняется, открытие чата возобновляет запись.

Решение, зарезервированные номера и прогресс хранятся в SQLite:
`chat.plan-decisions.<chatId>`. Резервирование идентичности предшествует записи
файла; повторное выполнение не создаёт дублей. Запись файла создаваемого
артефакта атомарна. При сбое файловой системы уже записанные файлы сохраняются,
а оставшиеся восстанавливаются по журналу; это не транзакция всего filesystem.

Старые карточки одного сохранённого плана, одного хода или связанного графа
объединяются при открытии чата. История сохраняется, замещённые карточки скрыты
из ленты и панели изменений. Уже созданные задачи и отказанные выборы
переносятся. Новые задачи не считаются подтверждёнными только потому, что
владелец раньше принял одну из старых карточек. Полностью принятый граф
продолжается без нового подтверждения; смешанный показывается целиком для
одного решения. Несвязанные предложения других ходов не объединяются.

При переходе от старых refs к `plan:<key>:<ref>` связь с созданной задачей
восстанавливается по результату прежней карточки с проверкой ref, названия,
этапа и спецификации в существующем файле. Новая связь сохраняется в журнале
до создания оставшихся задач; статусы, описания и результаты оригиналов не
перезаписываются. Одного совпадения названия недостаточно для присвоения
чужого номера. Неоднозначные совпадения и повтор задач внутри плана
отклоняются до записи. Создание сериализовано между чатами одного проекта,
с повторной проверкой существующих задач после предыдущего автора записи.

Конец ответа модели не завершает активное планирование. Сохранённый остаток
продолжается автоматически; после двух продолжений без прогресса или
двенадцати продолжений сообщается конкретная причина остановки. Сообщение
владельца имеет приоритет. `control_plan` приостанавливает, возобновляет или
отменяет операцию; отмена допустима по явному решению владельца. Одиночные
локальные задачи и пустые этапы доступны через прежние инструменты.

Проверки используют разрешённые владельцем изолированные записи настоящих
AppDb/ArtifactStore; browser-проверка — штатный Electron. Fake backend,
mock API и агентские сессии для этих проверок не используются.
