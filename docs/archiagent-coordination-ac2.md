# AC-2: общая память, версии входов и локальный кандидат

Дата: 12.11.2026. Статус: **завершён в рабочем дереве, локальная приёмка 11/11**.
Сборка, целевые проверки и сквозной сценарий Cat-pilot пройдены. Основание — [план AC-2](archiagent-coordination-plan.md#ac-2-общая-память-зависимости-и-preflight).
Изменения не являются релизом или завершением AC-3–AC-5/AG-1.

## Реализация

Все новые и восстановленные чаты используют сохраняемую идентичность AC-1.
Темы, история, авторы и выбранные модели остаются отдельными. Доступ модели
чата к основной рабочей копии сериализован исключительным lease RC-2: второй
чат ждёт до запуска модели, а незавершённая команда первого удерживает владение.
Задачи в отдельных worktree продолжают использовать собственные leases.

`ProjectMemory` предоставляет `read_project_memory`: индекс источников,
поиск и адресное чтение страниц. В индекс входят документы `.skaro/`, задачи,
публичные истории активных/архивных чатов и запусков этого проекта. Документ
имеет версию точных байтов; журнал — версию размера, времени изменения и inode.
Чтение проверяет версию повторно. В prompt попадают идентичность координатора
и ограниченный список ссылок, а не весь архив. Источник сохраняет `scope`,
автора и версию; ответ помечается `historical-evidence-only` и не выдаёт права.

Память не читает credential vault, приватные ответы, конфигурацию или сырой
протокол агента. Публичная проекция исключает reasoning/unknown; повторные
результаты чтения истории не размножаются рекурсивно. Метки паролей, токенов
и блоки private key дополнительно редактируются. Это не обещание распознавать
произвольный немаркированный секрет, который владелец сам записал в публичный
документ. Project scope и realpath проверяются до чтения, включая журналы.

Перед каждой доставкой задачи, включая существующую native session,
`taskPreflight` фиксирует требования, версии принятых SHA и критериев зависимостей,
контракт окружения с содержимым Compose, проверки, workflow и полномочия.
После ожидания допуска снимок сверяется повторно. Изменение требований
попадает в текущий контекст и журнал `task_inputs_changed`; изменившийся вход
во время работающего хода останавливает исполнение с сохранением работы.

Обычный старт с зависимостью в `review` по-прежнему запрещён D-45.
Разрешённые входы `review` и `done` подготавливает существующий integration
service. Проверяется принятый SHA; завершённая squash/rebase-публикация того же
результата также доказывает его наличие. Другая версия, незавершённая или
отменённая публикация таким доказательством не является. Удалённая после
публикации ветка не подменяет сохраняемый accepted SHA. Изменённые критерии
или транзитивные входы требуют новой проверки. Незакоммиченная работа не
перезаписывается интеграцией.

## Типизированные prerequisites и результаты

В `.skaro/config.yaml` добавлено необязательное поле `workflow`, индексируемое
ID существующих задач. Каждая запись имеет `id`, `kind`, `phase` и необязательный
`producedBy` — ID задачи-производителя:

| Поле | Контракт |
| --- | --- |
| `kind: artifact` | `path` внутри checkout и точный `sha256`; проверяются реальные байты |
| `kind: service` | `url` localhost/loopback без credentials; проверяется настоящий HTTP-ответ |
| `phase: prerequisite` | Проверка до исполнения, ребро к `producedBy` участвует в поиске цикла |
| `phase: result` | Проверка после реализации, перед submit/фиксацией локального кандидата |

Цикл кода/артефактов/сервисов и требование собственного будущего результата
отклоняются с конкретным объяснением до вызова модели. Частичный submit с
невыполненными критериями не требует наличия ещё не созданных результатов.
Статус задачи никогда
не заменяет готовность сервиса. Удалённые URL, неоднозначные ID, пути за пределы
checkout и неточные хеши отклоняются. Нового редактора workflow в UI на этом
этапе нет; используется существующий конфигурационный документ.

## Проверенный кандидат и постоянная локальная версия

Новый `purpose: local` использует тот же IntegrationService, очередь, checks,
служебный worktree и штатное окружение. Исходный checkout должен быть чистым,
HEAD и снимок входов — точными. Кандидат не публикуется в base и не меняет
статус задачи на `done`. Manifest фиксирует commit/tree, входы, проверки,
версию окружения, ID образов реально проверенных сервисов и health evidence.

Установка доступна через owner IPC `local.register`, `local.prepareCandidate`,
`local.candidate`, `local.install`, `local.rollback`. Исполнители — существующие
сервисы под контролем AC-1 и RC-2; MCP не получает права установки. Новые
кнопки, окна и режимы делегирования относятся к последующим UI/permissions-этапам.

Цель должна быть зарегистрированным persistent `project-dev` ресурсом проекта.
Проверяются canonical Compose path/project, поколение ресурса, конфигурация,
ревизия цели и manifest. Установка держит исключительный lease, а работающий
контур — отдельный бюджет окружения. Код размещается в независимом persistent
detached worktree, монтируется read-only; очистка task worktree его не удаляет.
Compose получает сохранённые immutable image IDs с `--no-build --pull never`.
После старта повторно проверяются изображения, health и объекты данных.

Manifest и цель должны иметь одинаковый `dataVersion`. Для writable persistent
данных кандидат требует явный `SKARO_DATA_VERSION`, цель — команды checkpoint
и restore. Skaro не копирует task-БД в постоянный контур и не считает одинаковую
строку версии доказательством совместимости произвольной миграции. Контракт
backup/restore обязан описывать реальный проект. Для контура без таких данных
используется `no-persistent-data`.

Receipt записывается до изменения контура и содержит предыдущий код, изображения,
контракт цели, объекты данных, состояние checkpoint и исходное running-состояние.
Откат допускается только для последней установки той же цели и сверяет контракт
заново; восстанавливает прежние образы/код, выполняет объявленный restore и health.
Если контур был остановлен, после проверки он снова останавливается.
Неоднозначный сбой не разрешает повторную установку поверх незавершённого receipt.

частичного submit повторно собран main штатной production-конфигурацией
Electron Vite (`resolveConfig` → Vite `build(config.main)`). Целевые тесты: 15 проверок

## Границы локальной приёмки

- Cat-pilot не содержит постоянной writable БД. Backup/restore базы, несовместимая
  миграция и авария ОС посреди установки не проходили живую проверку.
- Проверен штатный Compose с read-only bind кода. Не заявлена приёмка произвольных
  удалённых сред, Compose profiles, установки без Compose или ОС кроме Windows.
- В имеющихся чатах Cat-pilot нет структурированных decision-карточек; проверено
  чтение настоящего ранее записанного указания владельца с исходным автором/scope.
- D-45, цикл и future-result проверяются как чистая политика над существующими
  задачами в памяти. Для этих случаев не записываются фиктивные task-статусы.
  Новая зависимая задача и искусственная публикация в Cat-pilot не создаются;
  конфликтное слияние новых accepted SHA этим запуском не подтверждено.
- Код UI не менялся. Browser-снимок подтверждает реальный установленный Cat-pilot,
  а не готовность будущего окна архиагента. AC-3/AC-4 и общая AG-1 остаются открыты.
- Проверенные release/candidate worktree сохраняются с зарегистрированным
  владением; это не разрешение на удаление прежних пользовательских ресурсов.
  Автоматическое освобождение retained-версий относится к RC-3.
