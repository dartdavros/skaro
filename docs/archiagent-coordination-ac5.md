# AC-5 — миграция и восстановление координатора

Дата: 13.11.2026. Статус: **завершён, локальная приёмка 9/9** в описанных границах.
Изменения находятся в рабочем дереве; коммита и релиза нет.
RC-4, C4-3 и общая приёмка AG-1 этим этапом не запускаются.

## Реализованное поведение

- Идемпотентная metadata-миграция v1 включает обычные, task-bound и архивные
  чаты, текущие и retired runs. Канонические журналы, авторство, ответы,
  настройки нативных исполнителей и существующие отказы не переписываются.
  Отсутствующий execution intent становится остановленным. Отсутствующая
  политика координатора получает `confirm` без автоматических правил;
  `ask/auto/full` работника не становятся разрешением координатора.
- Неизвестный формат, повреждённый intent/policy и будущая версия migration
  закрывают новый dispatch. Старый inbox без доказуемого owner intent остаётся
  `uncertain` с исходными аргументами. Legacy blocker не становится готовностью.
- Входящий owner command получает неизменяемое происхождение и поколение допуска.
  `coordinator.setDispatch(project, enabled, expectedRevision)` использует CAS;
  отключение сохраняет историю и переводит ещё не доставленные команды в
  неопределённые. Повторное включение не восстанавливает прежнее поколение
  разрешений. Уже начатые действия завершаются под своими владельцами;
  Stop, отказ, отзыв и чтение доступны. Это технический owner API, нового UI нет.
- Старые startup batches сохраняют исходное поколение при recovery и handoff.
  Off снимает автоматическое execution-намерение; ни старая очередь, ни
  восстановление из одного legacy-диагноза не создают новый допуск. Существующие
  кандидаты интеграции сохраняются, но после off/on продолжение требует свежего
  сообщения/решения владельца через прежний executor. Это отзыв полномочий при
  отключении, а не дополнительный обязательный C4 gate обычного workflow.
- Admission модели повторно проверяет поколение после ожидания ресурса/квоты
  и непосредственно перед эффектом. Немодельный housekeeping сохраняет свой
  прежний допуск и не требует доступной модели.
- Recovery сверяет фактическое условие типизированного инцидента. Неопределённый
  эффект не запускается повторно. Снятие точного blocker и запись продолжения
  в существующий долговечный inbox выполняются одной SQLite-транзакцией.
  Stop, версия входов, актуальный run и другие блокеры проверяются заново.
- Новый owner-policy revision входит в identity нового инцидента. Свежий
  запрос не оживляет старый одноразовый отказ и не присваивается его записи.
  Identity ресурса/условия/поколения неизменяема при обновлении подписок.
- Принятые offline-ответы получают собственный долговечный UUID и epoch
  исходного turn. Повторный `req-0` адаптера больше не совпадает с предыдущей
  доставкой; recovery не закрывает новый вопрос старым ответом. Публичные
  native decisions разделены по owner/turn. Неоднозначный старый mailbox
  сохраняется для отдельной проверки, без автоматического подтверждения.

Реализация разделена на migration, dispatch/provenance, model admission,
incident recovery/delivery и независимые verification helpers. Новых UI
компонентов и отклонений от утверждённого AC-4 baseline нет.

## Границы и передача в AG-1

- Внешняя квота провайдера намеренно не исчерпывается. Реальная проверка
  ожидания выполняется через штатное ограничение аккаунта в resource policy,
  без подставной записи об исчерпании провайдера.
- Не проверяется каждый исторический чат вручную в UI: все scoped журналы
  проверяются по ссылкам, чтению и byte-prefix hash; browser-приёмка проверяет
  реальные task feed, общую очередь и журнал.
- Неизвестные legacy-полномочия и исходы требуют отдельного evidence/решения;
  удобный UI их административного разбора этим этапом не придумывается.
- Штатный выход из приложения отдельно **не зачтён**. После успешных browser
  assertions и подтверждённого Stop `electron.close()` не завершился;
  AppLifecycle предусматривает native confirmation при busy, но сам диалог
  не наблюдался: computer-use app approval истёк по timeout. Собственное дерево
  Electron закрыто по повторно проверенным PID/parent/path/birth; это записано
  в `teardown-proof.json`. Другие приложения не останавливались. После закрытия
  выполнен независимый SQLite/policy/resource audit выше.
- Дополнительного обязательного C4 gate не добавлено. Совместное поведение
  актуального C4 workflow, RC-4 и включение продукта проверяются отдельно в AG-1.
- Код и данные продуктовых задач не принимаются этим аудитом. T-006 остаётся
  на Codex с исходными зависимостями; T-004 не объявляется принятой по статусу.
