# C4-3 — реализация и приёмка

Дата: 13.11.2026. **C4-3 завершён в проверенном контуре Windows / Codex / Cat-pilot.**
Границы живой проверки и неисполненные варианты отдельно перечислены ниже;
общее включение, другие платформы и релиз этим статусом не объявляются.
Владелец утвердил [макет полного окна](archiagent-c4-3-design-proposal.md)
и явно поручил реализацию, сборку, целевые проверки и настоящую приёмку Cat-pilot.

## Реализация в рабочем дереве

- «Полный аудит» в существующей панели C4, включая отсутствие модели.
  Открытие раздела читает состояние; запуск — отдельная команда владельца.
- Один долговечный run и настоящий чат «Полный аудит C4». Повтор открытия
  показывает прежний run; новый запуск после итога требует его актуального ID.
- Используются штатные агент, read-only session policy, ресурсный допуск,
  MCP и координатор. Инструменты аудита ограничены чтением, предложением
  одного C4-пакета и сохранением проверяемого результата. Файлы не пишутся
  прямыми командами аудита; пакет применяется только существующим writer.
- Состояния в прежней «Фоновой работе», общие решения и прежняя карточка C4.
  У кнопок диалогов Lucide-иконки по прямому поручению владельца.
- Результат связывается с fingerprint реальных публичных текстовых источников,
  документов и модели. Неполные evidence не дают результата «расхождений нет».
  Используется source policy графа: credentials, runtime stores и бинарные
  файлы не передаются как текстовые исходники; лимиты сохраняют неполноту.
- Stop дожидается штатной остановки транспорта и процессов. Перезапуск
  восстанавливает состояние, не возобновляет остановленный аудит и сначала
  сверяет уже принятое применение.
- Миграция добавляет отдельные маршруты пакетов, исходных решений и зависимых
  task results. Исходные пакеты, их fingerprints, source scopes и protocol
  bindings не переписываются; project default не переключается этим UI.
- Ошибка применения сохраняет accepted и конкретный конфликт. Общая очередь
  сверяется с каноническим хранилищем C4, поэтому разрыв между записью согласия
  и публикацией в ленту не превращает accepted в новый вопрос. Pending,
  не успевший попасть в ленту, проецируется по исходному владельцу.
- Событие успешного применения появляется только после физического
  `c4.status === applied`. Повтор восстанавливает ту же журналируемую операцию.
- Startup barrier сверяет прежние C4-операции до активации owner inbox и native
  recovery. Исходный ответ связывается с package ID, revision, answer hash
  и fingerprint до dispatch. Только проверенное applied/rejected закрывает
  потерянный receipt и соответствующую uncertain IPC-операцию; accepted сам
  по себе не выдаётся за выполненное действие.
- По отдельному указанию владельца кнопка остановки уменьшена до 24 px;
  Lucide Square имеет размер 12 px, сплошную заливку и нулевую обводку.

## Согласованное применение и аварийное восстановление

Владелец ответил «Разрешаю пакет и аварийную проверку» на полный обзор
`c43-package-review-2fcaa711-d0aa-4225-852d-610f7afa681f/REVIEW.md`.
До нажатия настоящей кнопки «Применить» созданы две отдельные SQLite-копии
через VACUUM INTO с committed WAL, `integrity_check=ok`, fsync и SHA-256:

| База | SHA-256 |
| --- | --- |
| skaro.db | `3197c26e22b25dbbb9f64c7bcccb56f0afaabd17c4eae63d8b093d3b4562f0fc` |
| workspace.db | `752a1c28b3487ae4be6469fb4895a04bd07f641d6b4889e08ec8c6f7517c4080` |

Копии: `verification/c43-application-fefb6170-828c-4086-ace0-3946a22e9c09/`.
Перед применением сверены immutable payload и все пять before hashes.

Первый настоящий выход с кодом 87 сохранил accepted, исходный owner receipt
и IPC-операцию dispatching. Однако writer успел записать пакет до завершения
процесса. Assertion «файлы ещё не записаны» не прошёл; этот прогон сохранён
как неуспешный для заявленного рубежа **до первой физической записи**.
Отката, подмены состояния и повторного согласования не выполнялось.
Checkpoint исправлен: вызывающая сторона await-ит выход, а невозвращающаяся
ветка не позволяет следующему writer войти в очередь при отложенном exit.

Повторный checkpoint того же реального accepted выполнен уже на записанном
пакете: выход 87 перед новым dispatch writer, неизменные hashes/mtime.
Нормальный запуск затем завершил прежний accepted по существующему журналу:
модель ревизии 4, ровно пять согласованных файлов и штатный history/4.json,
неизменяемый исходный пакет, receipt done и та же IPC-операция succeeded.
Событие `c4_application_verified` появилось один раз (2192). После второго
перезапуска bytes, mtime, история, receipts и вопросы остались прежними.
Нового чата, задачи или model call при восстановлении не запускалось.

Успешный протокол:
`c43-accepted-recovery-e524ad82-aa47-49c5-922e-9d8d71ce35f2/proof.json`.
Screenshot `recovered-applied.png` просмотрен: итог в «Недавно», проверенное
событие применения, ссылка в исходный чат, без нового C4-вопроса. Два прежних
вопроса T-012/T-013 сохранены. Этот результат подтверждает реальное
восстановление **после записи и до завершения исходного ответа**, а не
непроведённый исходный обрыв до первой записи.

С первичной SQLite-копией дополнительно сверены все 24 прежних run rows,
две настоящие run bindings `impact-v1` и project default: байты не изменены.
Default остаётся `package-v1`. Протокол — `protocol-preservation.json`
в каталоге успешного восстановления. Реальный migration pending/accepted
пакета `impact-v1` не создавался; сопоставление такого пакета и неизвестный
protocol проверены только целевыми metadata tests.

## Найденный ресурсный blocker и завершающие проверки

Первая проверка ошибки транспорта (`c43-transport-12d4e5b9-e991-40ee-a84e-562e3ef61803`)
до сети не дошла: прежний audit chat `3baa6780-0e16-4d10-b67c-ea440eeb3379`
удерживал retained process/model/work и project-chat-controller после выхода.
Таймаут драйвера не объявлен ошибкой provider или пройденной UI-приёмкой;
новый аудит `77338209-9f26-4936-8afa-51959d140067` штатно остановлен.

Recovery теперь находит только retained process leases известных host-created
audit chats того же проекта; существующий TaskRunProcesses проверяет PID/birth
и останавливает принадлежащее им дерево. Только после подтверждения вызывается
штатный reconcileProcess для этого точного ключа/intent. При ошибке holdings
сохраняются, startup пишет диагностическое событие; явный новый Start повторяет
ту же проверку. Неизвестные владельцы, чужие проекты и обычные чаты этим C4
recovery не затрагиваются. Обычный detach также сверяет связанные leases после
подтверждённой остановки транспорта. Новый audit не обходит resource lock.
Настоящая повторная загрузка подтвердила verified OS stop и освобождение
четырёх исходных leases с evidence `previous_native_process_exit_confirmed`;
старые resource consumers удалены, process identity list пуст.
Протокол `process-recovery.json` в каталоге успешного accepted recovery.

Последующие попытки `c43-transport-96b07bfc-*`, `c43-transport-ed02eb80-*`
и `c43-transport-0eea7656-*` не засчитаны. В первой настоящий клиент выдавал
reconnect/error notifications, но не завершил turn за timeout. В следующих
PID отсутствовал из-за реального `budget_disk`: native-клиент ещё не был
допущен. Stop подтверждён; ожидание ресурса не выдано за ошибку provider.

Лимиты не менялись. Две собственные SQLite-копии сжаты прозрачным NTFS-сжатием,
без удаления или перемещения. Сохранено 874 299 392 байта (около 834 МиБ).
После сжатия повторно проверены оба SHA-256, integrity_check и fsync;
`ntfs-compression.json` находится рядом с копиями. Логические байты прежние.

Окончательный настоящий UI-прогон:
`c43-transport-406bb525-8181-490d-aefd-81cdc724c7d3/proof.json`, **passed=true**.
Использованы обычное соединение, настоящий настроенный Codex и read-only audit.
Только его записанный PID/birth проверен и штатно завершён OS executor:
реальный EOF дал сохранённый `error: Codex stopped (1)`, текст ошибки и
«Повторить» с Lucide. Обычный перезапуск сохранил тот же audit ID и ошибку,
не возобновил модель; новый пакет, изменение исходников и renderer exceptions
отсутствуют. Screenshot `error-after-normal-restart.png` просмотрен целиком.
Это управляемый отказ собственного клиента, не утверждение об outage provider.

Окончательная production-сборка main/preload/renderer, main types,
целевые ESLint/Prettier и NO GOD пройдены. Svelte-check после последней
renderer-правки — 0 errors / 0 warnings. 27 целевых тестов пройдены;
после окончательного detach повторены 5 непосредственно затронутых файлов /
8 passed. Полный suite не запускался.
Передача фактов — [handoff AG-1](archiagent-c4-3-handoff.md).

Итоговая read-only сверка и SHA-256 всех 71 code files и main-сборки:
`verification/c43-final-abae604c-f1c1-4e6f-b94e-fcb9fe7f6261/source-and-state.json`.
Пакет applied, модель 4, исходный receipt done, 24 прежних runs и обе
impact-v1 bindings сохранены. Активных/retained scoped holdings — 0.
Последний тестовый аудит намеренно хранит `Codex stopped (1)` после управляемого
отказа клиента; предыдущий согласованный пакет остаётся применённым.
Native retry не выполняется сам при открытии проекта.

## Закрытие критериев

| Критерий | Доказательство и граница |
| --- | --- |
| Design gate | Утверждённое полное окно, существующие компоненты, иконки и отдельное уточнение Stop. |
| Явный аудит | Настоящий native run, отсутствие запуска при открытии, один run после навигации, Stop и перезапуск. |
| Независимый граф | Детерминированный indexer; в настоящем окне индекс завершился независимо от saved error аудита, без нового чата/пакета/принятия C4. |
| Одно решение | Pending просмотр/«Позже»/restart, затем одна настоящая кнопка «Применить» и исходный receipt done; два чужих исторических вопроса сохранены. |
| Verified success | Пять after hashes, модель 4, штатная история, один verified event, без повторной записи bytes/mtime. |
| Миграция/совместимость | Реальные legacy pending/accepted и прежний applied пакет; 24 runs и две impact-v1 bindings сохранены. Impact owner package и конфликтные DTO — целевые metadata tests, не фикстуры живой приёмки. |
| Browser | Реальные running/Stop/pending/applied/error, навигация, defer, restart и отсутствие повторного C4-вопроса. Error — настоящее завершение собственного native-клиента. |
| Передача AG-1 | Команды, версия рабочего дерева, proof paths, результаты и ограничения записаны в handoff; AG-1 не запускался. |

Не заявляются macOS/Linux, другие adapters, power loss и искусственно
созданный конфликт пользовательской записи. Границы проверок и контроль
включения передаются в AG-1; релиз и общий default не включены.
