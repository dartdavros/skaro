# Допуск ресурсов и восстановление окружений

Исправление от 13–14.11.2026. Причина: запуск T-023 в Stolovka получил оценку
16 ГиБ / 16 CPU, затем оставил общую очередь проекта в `uncertain`. Вызовы
T-024 возвращали `queued`; оба блокера были привязаны к run вместо окружения.

## Измерения и оценка

- `mem_limit` / `cpus` Compose — верхние ограничения контейнеров, а не их
  потребление. Они больше не суммируются как необходимый резерв запуска.
- Потребность окружения оценивается по реальному `docker stats` своей копии,
  объявленного source либо зарегистрированного dev-контура этого проекта.
  Над измеренной нагрузкой сохраняется 25% запаса и единый минимальный envelope
  из ресурсной политики. Холодный запуск использует этот envelope один раз
  на окружение: количество сервисов и выключенные profiles его не умножают.
- Бюджет машины использует свежую свободную RAM/диск и измеренную долю idle CPU.
  Docker дополнительно ограничен реальным бюджетом daemon/VM. Неизвестные
  измерения остаются неизвестными и не открывают допуск.
- Уже наблюдаемое потребление зарегистрированного контейнера учитывается
  один раз. Credit привязан к точному object ID и live lease; новая выдача
  после снимка продолжает резервировать полный envelope. Неизвестные объекты
  и чужие идентичности не дают credit.

Оценка с запасом остаётся оценкой будущего расхода; она не выдаётся за замер
или гарантированную верхнюю границу памяти неизвестного приложения. Лимиты
владельца, резерв ОС, число исполнителей и обычная изоляция сохраняются.

## Ожидание и продолжение

`start_environment` из worker делает один реальный admission. Недостаток
ресурсов возвращает `environment_waiting_resource`, привязывает incident к
окружению и сохраняет точный intent. Worker завершает ход и освобождает
свою память/слот; контроллер продолжает тот же разрешённый запуск через
обычный Resource Manager. Истечение ожидания, изменение входов, deny или Stop
не превращаются в разрешение повторить действие.

Запуски и изменения конфигурации сериализуются по владельцу окружения,
включая legacy shared checkout. Чтение `configure_environment` /
`setup_environment` — observation, без project writer и ожидания Docker-очереди.
Неизвестный исход одного окружения не удерживает writer всего проекта.

Попытка исправления также включает digest подписчиков и их intent в operation ID:
новое явное поручение после Stop не переиспользует ID прежней отменённой попытки.
При выборе и замене host-портов учитываются bindings работающих Docker-контейнеров,
даже когда socket probe Windows/WSL считает такой порт свободным.

Состояние `resolved` требует настоящего readiness и актуального подписчика.
Только затем прежний durable inbox получает continuation. Подтверждённый Stop
сохраняется также при ответе на вопрос, восстановлении истории и новом intent.

## Неизвестный исход и старые записи

Прерывание до входа в lifecycle/build/start имеет отдельное доказательство
`EnvironmentNotDispatched`; оно завершает операцию как неисполненную, а не
оставляет `uncertain`. После restart тот же вывод допускается только из ledger,
который подтверждает отсутствие выданного environment grant. Retained/released
grant не является таким доказательством: неизвестный внешний эффект сохраняется.
Подтверждённый выход shell с ошибкой получает отдельный failed receipt с явным
предупреждением о возможных частичных эффектах. Это не доказательство их отсутствия
и не разрешение слепо повторить прежний operation ID.

Старый environment-блокер на run при появлении точной идентичности заменяется
новым incident на ресурс; исходная запись остаётся в истории с причиной замены.
Неопознанный ресурс не становится disposable/registered автоматически.
Неподдерживаемое исправление, изменившееся условие и исчерпание попыток получают
долговечный вопрос через существующую закреплённую QuestionCard. Ответ сохраняется
как ввод владельца, а не доказательство устранённой неисправности.

## Проверка

Адресные unit/SQLite проверки охватывают расчёт CPU/RAM, отсутствие двойного
учёта, изоляцию очередей, безопасное восстановление неисполненного запуска,
продление intent и fence ответа после Stop. Моки API и подставные сервисы
не используются.

Сквозной driver: `node apps/desktop/scripts/verify-environment-admission.mjs`.
Он требует свободного singleton штатного Skaro, выбирает Cat-pilot до
`createServices`, использует существующую read-only задачу T-010, настоящий MCP
и Compose. Ограниченный owner cap проверяет ожидание без подмены метрик;
исходная политика восстанавливается.

14.11.2026: production build, desktop main TypeScript, lint и 45 адресных тестов
в 21 файле прошли. Сквозная приёмка:
`userData/verification/environment-admission-d9c61a85-bd06-410b-8be1-ed22aa4c1b22/proof.json`.
Первый ответ MCP при исчерпанном owner cap вернулся за 4,95 с; configuration read
оставался доступным. Stop отменил ожидание без старта native worker. Новое намерение
получило отдельный operation ID, HTTP readiness на `http://localhost:20008` вернул
200 и точные байты настоящего `index.html`; incident стал resolved, Codex завершил
возобновлённый ход. Итоговая явная остановка сохранилась. Предыдущие упавшие прогоны
сохранены отдельно, а не переименованы в успешные.

В настоящем scoped Electron визуально проверены единственный проект Cat-pilot,
список задач, восстановленная лента T-010 и компоновка ввода. Сворачивание в трей
возвращено в исходное включённое состояние. Новый layout не добавлялся.
Каталог BYOK-моделей в этой UI-проверке не принимался: проверочный runtime требует
явный VPN proxy, а автоматическая проверка разрешений отклонила смену маршрута.
Проверка выполнялась без этого override; native Codex, MCP, Docker и resource
workflow проверены отдельно. Живой запуск Stolovka этой приёмкой не выполнялся.
