Дата: 13.11.2026. C4-1 реализован и локально проверен в рабочем дереве.

[Отсутствующие согласования и техническая сверка](archiagent-c4-3-design-gate.md).
[Контракт, проверки и ограничения C4-1](archiagent-c4-1.md).

Основания: [ADR-0049](adr/0049-project-archiagent.md),
[контракт архиагента](archiagent.md), [целевой процесс C4](c4-workflow.md).

C4-* — идентификаторы этапов документа, не автоматически созданные задачи Skaro.
Отметки C4-1 относятся к контрактному этапу, не к включению нового runtime.

## Исходные точки и границы

[c4.md](c4.md) описывает действующие модель, инструменты, транзакции и UI.
В legacy runtime отдельный пакет требует решения, а `submit_result`
проверяет pending-пакеты и сохранённое ревью. В C4-2 реализован явно выбираемый
`impact-v1` с независимой проверкой и immutable run binding; default остаётся
legacy. Общее включение и миграционная приёмка относятся к C4-3/AG-1.

| Существующая область | Изменение ответственности |
| --- | --- |
| `main/c4-service.ts`, `main/background/c4-work.ts` | Маршрутизация пакетов через решения архиагента с сохранением журнала и fingerprints. |
| `main/c4-review*.ts`, `main/c4-coverage.ts`, `main/c4-task-scope.ts` | Проверка доказательств и локального scope; отсутствие повторного смыслового ревью при независимой правке. |
| `main/c4-publication.ts`, `main/c4-candidate.ts`, completion | Проверенная публикация принятого planned без второго подтверждения; сохранение общих инвариантов. |
| `packages/core/src/c4/` | Валидация, узкие операции, конфликт версий и восстанавливаемая запись. |
| `packages/mcp-server/src/c4-tools.ts`, `main/c4-instructions.ts` | Контракт evidence/impact рабочего агента и совместимость действующих сессий. |
| `renderer/src/c4/`, общий механизм решений и фоновой работы | Ручной аудит и представление результатов через согласованный UI. |

Пути `main/` и `renderer/` относятся к `apps/desktop/src/`. Перед реализацией
повторно проверить актуальный код; таблица не предписывает разрастить эти файлы.
Модель операции, классификация, валидация, хранение, политика прав и UI имеют
отдельные модули. Порог около 180 строк для компонента и 300 для изменённого файла
сохраняется; одна feature не собирается в одном сервисе или компоненте.

## C4-1. Контракты влияния, классификация и совместимость

Зависимости: принятый ADR-0049. Контракт идентичности и событий согласуется
параллельно [AC-1](archiagent-coordination-plan.md), без ожидания его реализации.
Совместимый формат фиксируется до исполнения новых операций в C4-2.

Работы:

1. Описать версионированное сообщение evidence/impact: проект, задача, запуск,
   checkout/base, Git fingerprint, требования, элементы, проверки, источники
   и расхождения. Не передавать полную модель по умолчанию.
2. Разделить техническую синхронизацию, новое существенное решение,
   необязательную идею и блокирующее противоречие. Задать проверяемые границы;
   произвольная классификация агентом не является допуском.
3. Определить узкую операцию модели, область ревью, ожидаемую версию, основания,
   решение по правам и идемпотентный ключ. Сохранить общие проверки и `planned`.
4. Описать совместимость старых MCP-вызовов, pending/accepted-пакетов,
   восстановления, отката и привязки протокола к незавершённому запуску.
5. Зафиксировать соответствие старых gate новым условиям, чтобы необязательные
   предложения перестали блокировать только после безопасного переключения.

Приёмка:

- [x] На примерах реальных изменений различаются техническая синхронизация
  и изменение принятого решения; недостаточное evidence не автоприменяется.
- [x] Контракт позволяет объяснить, какие задачи ждут и почему.
- [x] Смена версии протокола не переинтерпретирует старое разрешение.
- [x] Существующие pending/accepted-пакеты и их история сохраняются неизменными.

Свидетельства и границы — в [отчёте](archiagent-c4-1.md). Старые writers/gates
не менялись; живой recovery pending/accepted остаётся приёмкой C4-3.

Проверки: целевые проверки классификации, области, fingerprints и совместимости
контрактов; разбор реальных сохранённых пакетов без их изменения. Не добавлять
тесты на перечисление полей ради количества и не создавать неразрешённые fixtures.

## C4-2. Проверка и синхронизация под управлением архиагента

Зависимости: C4-1, AC-2 (контекст, зависимости, preflight), AC-3 (блокеры и права).
Операции используют учёт RC-1 и допуск RC-2 при работе с checkout или запуске
ресурсоёмкой проверки; из фонового C4 нельзя обойти контракт ресурсов.

Работы:

1. Ввести маршрут evidence от рабочего агента к архиагенту и автоматическую
   проверку реализации принятого решения без отдельной карточки C4.
2. Сервисом разрешать только доказанную техническую синхронизацию. Существенные
   изменения направлять в одно решение по правам с точным составом задачи,
   спецификаций, ADR и модели. Ручное согласие не имитировать.
3. Удерживать только зависимые операции при противоречии; необязательную идею
   сохранять отдельно. Не снимать реальную зависимость ради завершения задачи.
4. Сериализовать записи, реализовать CAS и пересборку независимых операций.
   Локальные fingerprints сохраняют ревью при посторонних правках; пересечение
   проверяется заново. Глобальные инварианты валидируются на общем кандидате.
5. Объединить применение документов и модели восстанавливаемым журналом;
   обеспечить повторы без двойной записи и защиту пользовательских изменений.
6. Сохранить штатную публикацию `planned → current` с кодом. Сдача результата
   не объявляет неопубликованную архитектуру текущей.
7. Переключать выбранный совместимый протокол явно; до переключения старые
   gates продолжают работать. Сохранять диагностику и основание каждого решения.

Приёмка:

- [x] Обычная задача по принятой архитектуре завершает C4-проверку без вопроса.
- [x] Новый контракт/требование не прячется в автоматической синхронизации.
- [x] Необязательный пакет не блокирует сдачу; обязательное противоречие блокирует.
- [x] Две независимые задачи не инвалидируют ревью друг друга; конфликтующие
  правки не затирают друг друга и не используют устаревший fingerprint.
- [x] Отказ проверки путей, неполный родитель и planned/current проверяются честно.
- [x] Повтор события и прерывание записи/публикации восстанавливаются без потерь.
- [x] Смешение старого и нового протокола не создаёт обхода приёмки.

Закрыто 13.11.2026. [Отчёт](archiagent-c4-2.md) отделяет реальные T-012/T-013,
native review, browser и аварийное восстановление от protocol metadata tests
и контрфактических проверок модели только в памяти. Полная миграция legacy,
ручной аудит и общие UI-сценарии этим этапом не объявляются проверенными.

Проверки: только изменённые сценарии ревью, классификации, прав, конкуренции,
журналирования и публикации; штатная сборка после изменений кода. Интеграционные
проверки — в разрешённом реальном checkout, без mock API, fake backend и обходов.
Живые сценарии агента выполняются на зарегистрированном Cat-pilot со scope
проверки из [builtin-agent-project-scope.md](builtin-agent-project-scope.md).

## C4-3. Ручной аудит, общие решения, миграция и приёмка

13.11.2026: [design gate закрыт утверждением владельца](archiagent-c4-3-design-gate.md).
Утверждённая очередь AC-4 сохраняется. По поручению владельца подготовлен
[макет запуска и состояний аудита](archiagent-c4-3-design-proposal.md).
Владелец согласовал макет и поручил реализацию, сборку, целевые проверки и приёмку на Cat-pilot.

Зависимости: C4-2 и AC-4 (общие решения и активность). Финальная проверка
восстановления согласуется с AC-5 и RC-4; результат передаётся в AG-1.

Работы:

1. Согласовать дизайн запуска полного аудита в существующем разделе C4,
   состояния выполнения/ошибки/результата и их связь с проектным окном решений.
   До закрытия design gate не реализовывать отсутствующие визуальные решения.
2. Добавить явный ручной запуск аудита без генерации при открытии проекта.
   Аудит использует те же evidence, права, ресурсы и очередь применения.
3. Передавать проверенные существенные результаты в сохраняемую «Фоновую работу»;
   ожидания показывать через один источник решений, без повторных кнопок
   подтверждения в нескольких независимых записях.
4. Выполнить явное сопоставление существующих пакетов, решений и зависимых задач.
   Pending остаётся pending до предусмотренного решения. Accepted заканчивает
   прежнее журналируемое применение или сохраняет конкретный конфликт.
5. Проверить обновление и перезапуск с обоими протоколами, отмену аудита,
   восстановление решения и защиту истории. Не переписывать старые пакеты.
6. Обновить инструкции агентов и актуальные документы после фактического
   переключения, указать оставшиеся ограничения. Не представлять старые тесты
   или этот план как доказательство готовности нового процесса.

Приёмка:

- [x] Дизайн согласован; визуальная приёмка реализации остаётся отдельным критерием.
- [x] Открытие проекта/C4 не вызывает LLM; полный аудит запускается явно.
- [x] Граф индексируется независимо, без LLM и без принятия C4 за пользователя.
- [x] Ответ в общем окне закрывает одно решение и продолжает правильные операции.
- [x] Событие успешной синхронизации отражает проверенное применение.
- [x] Старые пакеты и решения переживают миграцию и перезапуск без подмены статуса.
- [x] Browser-проверка настоящего Skaro на Cat-pilot подтверждает ожидания,
  ошибки, переключение экранов, восстановление и отсутствие лишнего C4-вопроса.
- [x] AG-1 получил фактический протокол проверок, версии, результаты и ограничения.

Закрыто 13.11.2026: сборка, types/Svelte, lint/format и 27 целевых тестов
пройдены. Настоящий Cat-pilot подтвердил Stop, навигацию, явный native аудит,
pending diff/«Позже», одно разрешённое применение пакета 3 → 4,
восстановление исходного ответа и native/resources, повтор без записи и

повторный checkpoint accepted до нового dispatch. Свидетельства и границы

## Общие условия проверок

Для изменений только документации сборка и runtime-тесты не запускаются.
При реализации нужны штатная сборка и только тесты изменённого поведения;
полный прогон допускается перед релизом или по прямому поручению владельца.
Новые mocks, временные серверы, fixtures и seed-данные без отдельного разрешения
не создаются. Недоступный штатный контур является blocker, не поводом подмены.
Новые живые проверки не выполняются на Chatballs или пользовательской stolovka.

Протокол приёмки отделяет проверенный код от непроверенного UI и открытых
миграционных сценариев. Для UI обязательна фактическая browser-проверка
штатного приложения; скриншот макета не заменяет её. До закрытия всех значимых
критериев соответствующий этап остаётся незавершённым.
