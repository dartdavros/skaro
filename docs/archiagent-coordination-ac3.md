# AC-3: блокеры, полномочия и продолжение задач

Дата: 12.11.2026. Статус: **завершён в рабочем дереве, локальная приёмка 11/11**.
Основание — [план AC-3](archiagent-coordination-plan.md#ac-3-блокеры-права-и-управляемое-продолжение).
Это изменение рабочего дерева, не релиз и не завершение AC-4/AC-5/AG-1.

## Контракт incident

Используется существующая запись `coordination_entities` AC-1, без второго
несогласованного хранилища блокеров. Старые записи остаются читаемыми.
Новый `protocol` хранит причину, стабильный диагностический код, точную версию
ресурса, проверяемое условие снятия, фазу, число попыток, operation/decision ID
и подписчиков `{taskId, runId, inputs, intent}`. Публичный журнал задачи содержит
диагностику; общая запись содержит ссылки и хеш evidence, а не вывод с секретами.

Идентичность включает проект, ресурс, причину, код, версию и условие.
Название задачи и похожий текст ошибки не объединяют разные incidents.
Неизвестная нетипизированная ошибка получает код с хешем диагностики.
Конкурентные отчёты сериализуются по идентичности; повторный отчёт обновляет
подписку задачи. Обновление открытой записи использует CAS; разрешённую или
отменённую запись нельзя переписать. Новое возникновение после разрешения
получает новый incident ID.

`report_task_blocker` принимает прежний `reason` и структурированные поля
`cause`, `code`, `resource_id`, `condition`. Контроллер сам добавляет актуальный
run, снимок AC-2, intent и версию зарегистрированного ресурса. Произвольная
ссылка на ресурс другого проекта отклоняется. Ошибки очереди/подготовки и
terminal error адаптера проходят тот же путь без обращения к модели.
Для ошибки до появления run сохраняется startup intent; вымышленный запуск
агента не создаётся и автоматического продолжения такого запуска нет.

## Разрешение и продолжение

Фазы открытого incident: diagnosing → waiting/executing → verifying;
подтверждённое условие переводит основную запись в resolved. После двух
неуспешных попыток с теми же входами устанавливается exhausted. Служба
не запускает цикл переписки или повторные model calls. Один pending decision
переиспользуется, повторная проверка не создаёт новый одинаковый вопрос.

AC-3 регистрирует два ограниченных действия: запуск существующего task
environment через `TaskEnvironments` и повторную проверку prerequisites.
Это существующие исполнители, а не произвольный shell, установка пакетов,
новая модель, аккаунт или изменение системных настроек. Окружение проходит
обычный допуск RC-2; неизвестная стоимость Docker/памяти не обходится.
Неподдерживаемое исправление остаётся ожидающим решения владельца.

Версия окружения включает resource ID/generation/identity, Compose и
конфигурацию, HEAD checkout владельца. Перед dispatch и после ожидания
ресурсов повторно сверяются действие, политика, версия, срок и хотя бы один
актуальный подписчик. Успех запуска сам по себе не снимает блокер: нужен
настоящий readiness HTTP-ответ. Prerequisites проверяются штатным AC-2 verifier.

Каждый start/resume/stop изменяет сохранённую версию намерения задачи.
После снятия блокера продолжаются только актуальные run и снимки входов
с включённым intent. Другой открытый incident той же задачи сохраняет паузу.
Ответ на решение после явного stop не запускает исправление или задачу.
Повторная доставка continuation дополнительно проходит AC-2 и проверку intent.

Неоднозначная операция после рестарта не выполняется повторно вслепую:
сначала проверяется реальное состояние. Подтверждённый результат согласует
uncertain operation AC-1; без доказательства действие остаётся ожидающим.
Полная миграция/автоматическое восстановление всех чатов и очередей — AC-5.

## Права координатора

Политика хранится отдельно от sandbox/permissionMode рабочего агента.
Изменять её может только owner IPC; MCP модели не предоставляет такой операции.
Правило содержит точные kind/target и конечный верхний предел расхода;
политика имеет revision и срок. Unknown cost никогда не равен нулю.
Два локальных действия AC-3 не вызывают модель, их model spend равен нулю;
ресурсная стоимость всё равно учитывается RC-2.

| Режим | Основание dispatch |
| --- | --- |
| С подтверждением | Точное одноразовое решение владельца с action hash, revision и expiry |
| Автоматически | Действующее правило владельца для точного действия/ресурса |
| Делегированно | Отдельное сохраняемое решение координатора внутри действующего правила |

Для двух зарегистрированных рутинных действий делегированное решение принимает
детерминированная часть координатора по текущему evidence. Дополнительная
LLM-переписка для запуска остановленного сервиса не нужна. Проектный чат может
читать incidents и принимать ограниченное решение через `decide_project_incident`;
инструмент не расширяет политику, бюджет или доступ модели.

Явный deny/revoke имеет приоритет во всех режимах. Отзыв создаёт запрещающую
запись даже при автоматическом правиле без прежнего approval. Одноразовое
согласие расходуется одной попыткой dispatch и не разрешает вторую команду.
Для повторного запроса после отказа/расходования согласия владелец может
отменить incident через `incidents.cancel`; это не включает intent. Требуются
новое явное поручение и новый отчёт, прежний deny не переписывается.
Истёкшее/устаревшее решение не превращается в согласие под новой политикой.
Ответ из ленты связан с её задачей и конкретным decision ID. Старое решение
при замене или фактическом снятии блокера закрывается без записи вымышленного
ответа владельца.

До AC-4 используется существующая закреплённая `PermissionCard`, без нового
экрана, layout, иконок или цветов. Controller approval живёт независимо от
native turn и сохраняется при восстановлении истории. Native permissions
по-прежнему истекают с ходом. Глобальное окно и события в модалке фоновой
работы этим этапом не реализованы.

## Раздельные причины и восстановление

| Причина | Условие продолжения |
| --- | --- |
| Environment / prerequisite | Реальная готовность сервиса или проверка актуальных входов |
| Quota | Новое наблюдение лимитов того же managed account, известный положительный остаток всех окон |
| Authentication | Новое authenticated status того же аккаунта |
| Rate limit | Ожидание; время reset или subscription quota не доказывают доступность RPM |
| Budget | Явное решение владельца; лимит и модель сами не переключаются |
| Context | Новое явное действие владельца/штатное управление сеансом, без бесконечного replay |
| No progress | Остановка автоматических попыток до нового явного намерения |
| Secret / owner decision / неизвестная внешняя причина | Существующий защищённый ввод/решение, без предположения об успехе |

Проверка провайдера не вызывает модель. Неизвестный остаток, смена аккаунта
или недоступная проверка не считаются восстановлением. AC-3 не предоставляет
автоматическую смену модели/аккаунта; так невозможно обойти исходную политику.
Квоты специально не исчерпывались для тестирования.

## Критерии приёмки

Уровни доказательства различаются: unit/SQLite проверяют контракты, live —
описанный реальный сценарий Cat-pilot; намеренные сбои провайдера и все
одновременные сочетания задач не объявляются живой приёмкой.

| Критерий AC-3 | Результат и evidence |
| --- | --- |
| 1. Общий incident, разные причины/версии отдельно | Выполнен: контракт идентичности и нескольких независимых подписок; live два конкурентных отчёта об одном остановленном сервисе |
| 2. Ошибка без работающей модели | Выполнен: controller capture очереди/startup/terminal error; типизированные limit/error причины проверены unit; live controller зарегистрировал реальный неготовый сервис до обращения к модели |
| 3. Одно исправление, проверка, актуальные intent | Выполнен: live attempts=1, succeeded/resolved, продолжение прежнего native session; snapshot/run/intent guards |
| 4. Предел без прогресса, нет повторных вопросов | Выполнен: максимум две попытки на incident, одноразовое согласие на одну; live повторный reconcile сохранил decision ID; no-progress и intent unit |
| 5. Матрица прав | Выполнен: чистые policy/dispatch tests всех трёх режимов — allow, deny, revoke, consumed, expiry, другой scope/version и unknown cost; live confirm stop/allow и delegated dispatch |
| 6. Делегирование без расширения | Выполнен: только bounded actions и owner rules; отдельный автор/основание; live coordinator approval без дополнительной модели |
| 7. Ответ не снимает stop | Выполнен: intent unit и live stop → allow_once без команды/модели; UI stop → deny |
| 8. Разные лимиты и восстановление | Выполнен в контракте: отдельные typed causes и правила таблицы выше; свежий provider status/limits, без предположений по reset timer |
| 9. Unknown spend и смена модели/аккаунта | Выполнен: null/нечисловой расход запрещён, смена аккаунта не проходит evidence, автоматического provider/model switch нет |
| 10. Независимость и освобождение RC | Выполнен локально: waiting task без lease, repair через RC-2, native continuation и отдельный ручной review lease; общий multi-task stress остаётся AG-1 |
| 11. Проверки и структура | Выполнен: 22 целевых теста, build/typecheck/lint, реальный workflow, browser-проверка полного Skaro и NO GOD |
