# AGENTS.md

## Авторизация изменений

- Без явного указания владельца не менять файлы. Вопрос или просьба посмотреть
  реализацию не разрешает правки; прямое поручение изменить или «делай» разрешает.
- Соблюдать конвенцию коммитов: emoji + conventional commit. Коммит выполнять
  только в рамках поручения владельца.

## UI / дизайн: актуальный baseline

По указанию владельца от 01.10.2026 актуальный дизайн уже находится в коде.
Источник: `apps/desktop/src/renderer/src/` и `packages/ui/src/`.
Правила и точки входа описаны в [docs/ui-baseline.md](docs/ui-baseline.md).

- Старые HTML-макеты удалены и больше не являются источником дизайна.
  Не восстанавливать прежний UI из истории Git или исторических заданий дизайнеру.
- Структура, иерархия, порядок, тексты, иконки, цвета, размеры, состояния,
  анимации и поведение сохраняются как в текущем baseline.
- Отклонения и новые UI-решения — только по прямому указанию владельца.
  Не упрощать интерфейс и не придумывать отсутствующие состояния.
- Если согласованного дизайна или состояния нет, остановить зависимую работу
  и запросить решение владельца. Временный UI не считать готовым продуктом.
- Перед UI-правкой изучить текущие компоненты и актуальные документы; после
  сверить результат визуально с baseline и разрешённым изменением.
- Ленту и взаимодействия агентов сверять также с `docs/agent-output.md`.
  Исторические задания `docs/design-brief-*.md` не переопределяют текущий дизайн.

## Достоверность локальной проверки

- Использовать штатный контур проекта: настоящий backend, compose/dev-скрипты
  и сервисы из документации. Если инструмент недоступен, проверить Docker,
  когда в проекте предусмотрены его файлы.
- Без отдельного явного разрешения не создавать и не запускать mock API,
  fake backend, временные HTTP-серверы, fixtures, seed-данные и другие заглушки.
  Правило распространяется на тесты, временные файлы и процессы вне репозитория.
- Не выдавать preview, неполные API-ответы или интерфейс поверх заглушек за
  штатно запущенный проект либо успешную проверку.
- При недоступном штатном контуре сообщить blocker и запросить указание
  владельца; самостоятельно подменять окружение нельзя.

## Engineering rules

- Соблюдать DRY, KISS, SRP, separation of concerns и NO GOD FILES.
- Не собирать полноценную страницу, feature или крупный workflow одним файлом.
- Компонент больше примерно 180 строк или со смешанными layout, state,
  data/model и subviews разделить до завершения задачи.
- Если новый или изменённый файл из-за текущей работы превышает примерно
  300 строк, вынести части в меньшие модули до финального ответа или коммита.
- Page-компоненты преимущественно собирают subviews; model/data и повторяемый
  UI выносятся отдельно. Новый компонент не владеет несвязанными обязанностями.
- Не дублировать сложный UI. Если требования нельзя выполнить с такой
  структурой, сообщить blocker вместо поставки плохой реализации.

## Проверки и Definition of Done

- Для документации без изменения кода не запускать сборку и runtime-тесты.
- Для мелких локальных UI-правок (CSS, размер, цвет, отступ, перестановка,
  текст) сборка — только по прямому указанию владельца.
- Для остальных изменений кода перед «готово» или коммитом должна пройти
  сборка и тесты изменённого кода и непосредственно затронутых сценариев.
- Полный прогон — только перед релизом или по прямому указанию владельца.
  Завершение задачи, коммит, сборка и локальный пакет не являются основанием.
- Писать только тесты значимого поведения и требований задачи, без тестов
  ради количества. Разрешение на заглушки не подразумевается запуском тестов.
- Для UI-изменений выполнить browser-проверку штатного проекта.
- Проверить изменённые файлы на NO GOD violations, компоненты — на отдельную
  ответственность, UI — на отсутствие несогласованных элементов и состояний.
- Явно сообщить о непроведённых проверках и отклонениях от baseline/docs.
